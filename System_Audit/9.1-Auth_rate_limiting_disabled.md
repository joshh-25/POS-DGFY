# ✅ RESOLVED - 9.1 Authentication Rate Limiting Disabled

## User Feedback
> Enable it, but always remember that if needed for testing, we can disable it at any time and nothing is affected in the production server

## Finding Description
The `authLimiter` middleware is defined as a pass-through function, leaving login endpoints vulnerable to brute-force.

## Severity
🟠 High

## Proposed Plan

### 1. Root Cause Analysis
In `backend/src/middleware/rateLimiter.js`:
- `authLimiter` is explicitly disabled (Lines 49-70).
- **Code**: `export const authLimiter = (req, res, next) => next();`
- The actual implementation using `rateLimit` is commented out.
- **Vulnerability**: Brute-force attacks on `/api/v1/auth/login` and `register` are not throttled at the application level.
- **Severity**: High (allows password guessing).

### 2. Applied Changes
Instead of a blanket middleware, the `authLimiter` is now applied **selectively** to ensure authenticated routes (like `/logout`) are not penalized by strict anti-brute-force limits.

#### A. server.js
Removed the blanket `authLimiter` from the `/api/v1/auth` mount.
```javascript
// Before
app.use('/api/v1/auth', authLimiter, authRoutes);

// After
app.use('/api/v1/auth', authRoutes);
```

#### B. routes/auth.js
Applied `authLimiter` directly to the target routes.
```javascript
router.post('/register', authLimiter, validateRegister, authController.register);
router.post('/login', authLimiter, validateLogin, authController.login);
```

### 3. Verification Results
1.  **Stress Test**: Running 10 login/logout cycles in a row now works without any `429` errors.
2.  **Brute Force Check**: Sending 6 consecutive login attempts to `/api/v1/auth/login` correctly triggers `429 Too Many Requests`.

### 4. Summary of Protection
- `/login`, `/register`: Protected by `authLimiter` (5 req / 15 min).
- `/logout`, `/refresh-token`: Protected by JWT/Token validation + `generalLimiter` (100 req / 15 min).
- `/lookup`: Protected by `lookupLimiter` (5 req / 15 min).
