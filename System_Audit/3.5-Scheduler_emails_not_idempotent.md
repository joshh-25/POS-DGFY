# Implementation Plan - 3.5 Scheduler email notifications are not idempotent

## User Feedback
> Make a plan that will not make the scheduler create a problem like this when restarting

## Finding Description
`checkExpiringSubscriptions` sends emails based on a date range check but handles no state to track "email sent".

## Severity
🟢 Low

## Proposed Plan

### 1. Root Cause Analysis
In `backend/src/schedulers/billingScheduler.js`:
- The query selects all tenants whose `current_period_end` is within a range (e.g., 7 days).
- It iterates and sends emails.
- **Problem**: It never records *that* it sent the email.
- **Scenario**: Scheduler runs at 00:00. It sends 10 emails. It crashes at 00:01. Automatic restart runs it again at 00:02. It selects the same 10 tenants and sends duplicates.

### 2. Proposed Changes
Implement "Stateful Notifications".

#### A. Migration: Add columns to `Tenants`
Add `last_expiry_warning_at` (Date) and possibly `last_notification_type`.

```javascript
// Migration
await queryInterface.addColumn('tenants', 'last_expiry_warning_at', {
  type: Sequelize.DATE,
  allowNull: true
});
```

#### B. Modify `checkExpiringSubscriptions`
1.  Filter out tenants who were already notified *today*.
2.  Update the record *after* sending.

```javascript
// Query
const expiring = await Tenant.findAll({
    where: {
        // ... dates ...
        last_expiry_warning_at: {
             [Op.or]: [
                 null, 
                 { [Op.lt]: startOfToday } // Only if sent BEFORE today
             ]
        }
    }
});

// Loop
for (const tenant of expiring) {
    await emailService.send(...);
    await tenant.update({ last_expiry_warning_at: new Date() });
}
```

### 3. Verification Plan

#### Automated Test
1.  Seed a tenant expiring in 7 days.
2.  Run scheduler. Expect email sent (mocked).
3.  Run scheduler again immediately.
4.  **Expect**: No email sent (Idempotency).

#### Manual Verification
1.  Run the scheduler manually.
2.  Check DB: `last_expiry_warning_at` is updated.
3.  Run again.
4.  Check logs: Tenant skipped.

### 4. Risk Assessment
- **Impact**: Low (prevents spam).
- **Mitigation**: Ensure the database update is efficient.
