# Audit 3.5 - Scheduler email notifications are not idempotent

## Status
Resolved

## Severity
Unspecified

## Root Cause
Without notification state tracking, scheduler restarts or repeated runs can send duplicate expiry emails to the same tenant on the same day.

## Fix Implemented
1. Notification state is stored on tenant records.
- Fields:
  - `last_expiry_notified_at`
  - `last_expiry_notification_type`
- Evidence:
  - `backend/src/models/Landlord/Tenant.js` (around lines 95-104)
  - `backend/migrations/20260219200000-add-notification-tracking-to-tenants.cjs`

2. Expiry-warning query is idempotent by date + type.
- `checkExpiringSubscriptions` excludes tenants already notified today for the same warning type (`7-day` or `1-day`).
- Evidence: `backend/src/schedulers/billingScheduler.js` (around lines 73-83).

3. Scheduler marks notification state after successful send.
- After `sendSubscriptionExpiringEmail`, tenant row is updated with notification timestamp/type.
- Evidence: `backend/src/schedulers/billingScheduler.js` (around lines 97-107).

4. Cluster-safe run locking reduces duplicate execution.
- Daily scheduler acquires/release distributed lock key `scheduler:billing:daily_check`.
- Evidence: `backend/src/schedulers/billingScheduler.js` (around lines 19-24 and 37).

## Test Evidence
1. Repro script
- `backend/scripts/verify_scheduler_idempotency.js`
- Creates/updates an expiring premium tenant, runs `checkExpiringSubscriptions()` twice, and asserts timestamp does not change on second pass.

2. Code-level behavior check
- Batch loop uses `offset: 0` with state-changing updates, so processed records leave the filter and are not reprocessed in the same run.
- Evidence: `backend/src/schedulers/billingScheduler.js` (around lines 85-87 and 103-110).

## Residual Risk
Without notification state tracking, scheduler restarts or repeated runs can send duplicate expiry emails to the same tenant on the same day.

The previously documented gap is now closed with dedicated Jest coverage:
- `backend/tests/billingScheduler.idempotency.test.js`
- `backend/tests/billingScheduler.db.integration.test.js`

Covered assertions:
1. No duplicate send on immediate rerun for 7-day warnings.
2. 1-day warning path is also idempotent on rerun.
3. Type-based behavior is correct (`1-day` vs `7-day`).
4. Failure path is safe: notification markers are not updated when email send fails.
5. DB-backed integration confirms real tenant row mutations and query filtering behavior.
