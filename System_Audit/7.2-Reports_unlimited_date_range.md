# Implementation Plan - 7.2 Unlimited Date Range in Reports (DoS Risk)

## User Feedback
> We should implement an acceptable date range limit

## Finding Description
Report endpoints lack maximum range limits, allowing requests that span decades and crash the server.

## Severity
🟡 Medium

## Proposed Plan

### 1. Root Cause Analysis
In `backend/src/controllers/reportController.js`:
- The `extractDateFilters` helper (Lines 4-13) simply passes `req.query.startDate` and `endDate` to the service.
- It does **not** validate that:
    1.  Dates are valid.
    2.  `endDate` is after `startDate`.
    3.  The range (diff) between them is reasonable.

In `backend/src/services/reportService.js`:
- `getProductionReport` (Lines 285-428): If `filters` is empty, it queries **ALL** `JobOrder`s and **ALL** consumption `StockMovement`s in the database.
- `StockMovement` table typically grows to millions of rows.
- **Vulnerability**: A malicious or accidental request to `/api/v1/reports/production` without parameters will attempt to load the entire transaction history into RAM, causing a Crash / DoS.

### 2. Proposed Changes
Enforce Default Ranges and Maximum Limits.

#### A. Modify `extractDateFilters` in `reportController.js`
1.  Parse dates with `Date.parse()` to ensure validity.
2.  Set default `endDate` to NOW.
3.  Set default `startDate` to 30 days ago (if missing).
4.  Enforce MAX range (e.g., 365 days). Throw 400 if exceeded.

```javascript
/* reportController.js */
const extractDateFilters = (req) => {
  const { startDate, endDate } = req.query;
  const now = new Date();
  
  // Default End: Now
  let end = endDate ? new Date(endDate) : now;
  if (isNaN(end.getTime())) end = now;

  // Default Start: 30 days ago
  let start;
  if (startDate) {
      start = new Date(startDate);
      if (isNaN(start.getTime())) start = new Date(now.getTime() - 30 * 24 * 60 * 60 * 1000);
  } else {
      start = new Date(end.getTime() - 30 * 24 * 60 * 60 * 1000);
  }

  // Validation: End > Start
  if (end < start) {
      throw new Error("End date must be after start date");
  }

  // Validation: Max Range (e.g., 1 Year)
  const diffDays = (end - start) / (1000 * 60 * 60 * 24);
  if (diffDays > 366) {
      throw new Error("Date range cannot exceed 1 year. Please narrow your search.");
  }

  return {
      startDate: start,
      endDate: end
  };
};
```

*Note: The Service logic expects string or Date objects. It's safer to pass Date objects or ISO Strings.*

### 3. Verification Plan

#### Automated Test
1.  Request `/api/v1/reports/production` with NO params.
    - **Expect**: Success (returns last 30 days data).
2.  Request with `startDate=2000-01-01`.
    - **Expect**: 400 Bad Request ("Date range cannot exceed 1 year").

### 4. Risk Assessment
- **Impact**: Medium (API Contract Change).
- **Breaking Change**: Clients relying on "Give me everything since the beginning of time" will break.
    - *Mitigation*: The UI likely selects dates. If the UI defaults to "All Time", it needs update. But usually, Reports UIs default to "This Month".
    - *Note*: "Expiry Report" might genuinely need "All future dates". We should exempt `getExpiryReport` (future dates) or apply different logic.
    - *Refinement*: `getExpiryReport` looks for `received_date` (past) in `reportService` logic. Since it filters Active Batches, the dataset is bounded by *Inventory Size*, not *Time*. It is safer. But `getProductionReport` queries *History*.
    - **Decision**: Apply strict limits to *History* reports (`production`, `po_analysis`). Apply looser or no limits to *Snapshot*/*Status* reports (`expiry`, `stock_aging` - which are bounded by current stock).
