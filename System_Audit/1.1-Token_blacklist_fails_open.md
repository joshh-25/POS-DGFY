# Implementation Plan - 1.1 Token blacklist fails open when Redis is down

## User Feedback
> I agree with this. Redis should be insanely utilized and have the correct usage for it

## Finding Description
`isTokenBlacklisted()` returns `false` when Redis is unavailable. This means a logged-out token will still be accepted if Redis goes down.

## Severity
🔴 Critical

## Proposed Plan

### 1. Root Cause Analysis
The `isTokenBlacklisted` function in `authService.js` explicitly catches Redis connection errors and returns `false`. This design choice prioritizes availability over security ("Fail Open"), allowing potentially revoked tokens to work if the cache layer is down.

### 2. Proposed Changes
We will switch to a **"Fail Closed"** strategy to ensure security compliance.

#### A. Modify `isTokenBlacklisted` in `backend/src/services/authService.js`
- Remove the `try-catch` block that suppresses errors.
- Allow Redis errors to propagate up the stack.
- This ensures that if we cannot verify the blacklist status, we assume the worst (security risk) and deny access.

```javascript
export const isTokenBlacklisted = async (token) => {
  // Let this throw if Redis is down.
  // The caller (auth middleware) must handle the unavailability.
  const blacklistKey = `blacklist:token:${token}`;
  const result = await cacheService.get(blacklistKey);
  return result === 'true';
};
```

#### B. Update `authenticate` Middleware in `backend/src/middleware/auth.js`
- The existing `try-catch` block in `authenticate` already catches errors and passes them to `next(error)`.
- By allowing `isTokenBlacklisted` to throw, the request will naturally fail and be routed to the global error handler.
- We will add a specific check to catch `Redis` related errors if we want to return a 503 "Service Unavailable" specifically, but generally, a 500 error is an acceptable outcome for a critical infrastructure failure.

### 3. Verification Plan

#### Automated Test
1.  Mock `cacheService.get` to throw an error (simulating Redis down).
2.  Send a request to a protected endpoint with a valid token.
3.  **Expect**: The request should fail (500 Internal Server Error) instead of succeeding.

#### Manual Verification
1.  Stop the Redis service (`docker stop redis` or Stop in Service Manager).
2.  Attempt to use a logged-out token (or any valid token).
3.  **Expect**: Access denied.

### 4. Risk Assessment
- **Impact**: High. If Redis goes down, **ALL** authenticated requests will fail. The system becomes unusable until Redis is restored.
- **Mitigation**: This is "Insane Utilization" as requested. For a critical security feature like revocation, the system *should* stop if it cannot guarantee safety. To mitigate, Ensure Redis has high availability (persistence, monitoring, auto-restart).

## Resolution
**Status: Resolved**
**Date: 2026-02-16**

The "Fail Open" vulnerability has been addressed by implementing a **Fail Closed** strategy for production environments while maintaining developer experience.

1.  **Fail Closed (Production Security)**:
    - `authService.js` now uses `cacheService.getCritical()`, which throws an error if Redis is configured but unavailable.
    - This error propagates to the `authenticate` middleware, resulting in a 500 error (denying access) instead of allowing the request to proceed.
    - This ensures that if the revocation list cannot be checked, the token is treated as potentially revoked.

2.  **Fail Open (Development Concession)**:
    - If `REDIS_URL` is explicitly *not configured* in the environment (e.g., local dev), the system logs a warning and allows the request.
    - This prevents development environments from crashing without Redis, while ensuring production (where `REDIS_URL` is mandatory) remains secure.

3.  **Crash Fix**:
    - Addressed a `ReferenceError` that caused 500 crashes when logging the fail-open warning.
