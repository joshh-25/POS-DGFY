# Implementation Plan - 5.1 Critical "Lost Update" Race Condition in Stock Movements

## User Feedback
> Make a plan that will prevent the inventory ledger corruption. How should we approach simultaneous stock movements so that data integrity is 100% accurate

## Finding Description
`createStockMovement` reads `current_stock`, calculates new value in memory, and writes it back without locking. Simultaneous updates overwrite each other.

## Severity
🔴 Critical

## Proposed Plan

### 1. Root Cause Analysis
In `backend/src/services/itemService.js`:
- Line 604: `const item = await Item.findByPk(itemId);`
- **Issue 1**: The read happens *outside* the transaction created at line 601.
- **Issue 2**: No row lock is applied.
- **Scenario**:
    - User A reads Stock=10.
    - User B reads Stock=10.
    - User A subtracts 2, saves 8.
    - User B subtracts 3, saves 7.
    - Final Stock is 7. Correct should be 5.

In `backend/src/services/stockMovementService.js`:
- Line 74: `const item = await Item.findByPk(item_id, options);`
- It uses the transaction, but **no lock**. Standard `SELECT` allows concurrent reads.

### 2. Proposed Changes
Implement **Pessimistic Locking** (SELECT ... FOR UPDATE).

#### A. Modify `itemService.js`
Ensure the initial fetch uses the transaction and applies a lock.

```javascript
/* itemService.js */
const item = await Item.findByPk(itemId, { 
    transaction,
    lock: transaction.LOCK.UPDATE // <--- Critical Fix
});
```

#### B. Modify `stockMovementService.js`
Apply the lock when fetching the item to calculate new stock.

```javascript
/* stockMovementService.js */
const item = await Item.findByPk(item_id, {
    ...options,
    lock: true // or transaction.LOCK.UPDATE
});
```

#### C. Alternative: Atomic Increment/Decrement
For simple updates, `item.increment('current_stock', { by: quantity })` is safer, but since we have complex logic (FIFO batches, expiration, logging) that depends on the *value* of the stock, Row Locking is the correct approach to ensure the in-memory value matches the DB value for the duration of the transaction.

### 3. Verification Plan

#### Automated Test (Concurrency)
1.  Create an Item with Stock=10.
2.  Launch 5 parallel requests to `createStockMovement` (deduct 1).
3.  **Expect**: Final Stock = 5.
4.  **Current Behavior (Fail)**: Final Stock is often 8 or 9.
5.  **Fixed Behavior**: Database manages locks, requests serialize, Final Stock = 5.

### 4. Risk Assessment
- **Impact**: High (Data Integrity).
- **Performance**: Row locking reduces concurrency for *the same item*. This is acceptable/necessary for inventory accuracy. It does not block other items.
- **Deadlocks**: Potential risk if multiple resources are locked in different orders. We must ensure consistent locking order (e.g., always lock Item before Batch).
