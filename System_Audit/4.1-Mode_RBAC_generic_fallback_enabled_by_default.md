# [PARTIAL] 4.1 Mode RBAC Generic Fallback Enabled by Default

Severity: High
Audit area: Authorization, tenant mode governance

## Re-Baseline Update (2026-08-21)

Source-level remediation is complete for the production default: `modeRbacFallback.js` defaults to disabled in production, and production validation rejects an explicit truthy override. Non-production retains the compatibility default. Legacy user remapping, fallback-use telemetry, and release evidence remain operational follow-up work, so this finding is not fully resolved.

## Finding

The mode-aware RBAC generic fallback remains enabled by default outside production for legacy compatibility; hosted production now defaults it off.

## Evidence

- `apps/dgfy-api/src/config/modeRbacFallback.js` defaults the fallback off when `NODE_ENV=production`.
- `apps/dgfy-api/src/config/productionEnvValidation.cjs` rejects a truthy production override.
- `apps/dgfy-api/tests/modeRbacFallback.test.js` and `apps/dgfy-api/tests/productionEnvValidation.test.js` cover the production behavior.
- `docs/testing/pos-readiness-status.md` identifies the temporary generic fallback window as remaining RBAC risk.

## Why This Matters

Mode-aware authorization is a core tenant safety control. A default-enabled generic fallback can mask incomplete role mapping and keep broad legacy permissions alive longer than intended.

## Required Remediation

1. Complete legacy role remapping workflow and runbook.
2. Flip production default to disabled once migration is complete.
3. Add release gate evidence that production tenants no longer require fallback.
4. Keep any emergency fallback explicit, time-bound, and logged.

## Acceptance Gates

- [x] Production default disables generic fallback.
- [ ] Legacy unmapped accounts have a governed remediation path.
- [x] Authorization tests cover fallback disabled behavior.
- [ ] Any fallback usage emits audit logs and alerts.
