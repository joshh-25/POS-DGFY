# 10.3 Inconsistent API Error Handling

**Severity**: 🟢 Low

## Proposed Plan

### 1. Root Cause Analysis
- **Current State**:
    - `api.js` interceptor logs 422 errors but returns `Promise.reject()`.
    - `Items.jsx` and `Dashboard.jsx` use `try/catch` or hook-based `error` state to show UI alerts.
    - `Layout.jsx` (UserProfile) `try/catch` block **swallows** errors (logs to console only).
- **Inconsistency**:
    - detailed user feedback in some places.
    - silent failures in others.
    - No Global Error Boundary to catch "Render Phase" errors if a hook explodes.

### 2. Proposed Changes
Standardize error handling.

#### A. Create `ErrorBoundary.jsx`
Create a global error boundary to wrap the App.

```javascript
/* components/common/ErrorBoundary.jsx */
// Standard React Error Boundary implementation
// render() { if (hasError) return <ErrorPage /> }
```

#### B. Wrap App in `main.jsx`
```javascript
<ErrorBoundary>
  <BrowserRouter>
     <App />
  </BrowserRouter>
</ErrorBoundary>
```

#### C. Standardize hook error reporting
Encourage `toast.error()` usage in `api.js` for 500 errors (Server Errors), so individual components don't have to handle "Server Exploded" logic.

### 3. Verification Plan
1.  Force a 500 error in Backend.
2.  Navigate to Dashboard.
3.  **Expect**: Generic "Something went wrong" toast (if global) or Component Error State.
4.  **Current**: Component Error state (Dashboard) or Silent Fail (Layout).

### 4. Risk Assessment
- **Impact**: Low (UX consistency).
- **Complexity**: Low.

### 5. Files to Change
- `frontend/src/components/common/ErrorBoundary.jsx` (New)
- `frontend/src/main.jsx`
