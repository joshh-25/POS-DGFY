## Finding Description
`handlePaymentCompleted` in `paymentController.js`:
```javascript
// BROKEN — always extends from today
const newPeriodEnd = new Date();
newPeriodEnd.setDate(newPeriodEnd.getDate() + 30);
```
Three failure scenarios:
1. **Duplicate webhook**: PayPal retries → second run sets `now + 30` again → harmless if same day, but drifts if days apart.
2. **Late webhook**: A webhook from last month arrives late → `now + 30` is less than the current `current_period_end` → tenant loses paid days.
3. **Mid-period webhook**: Renewal fires on the 15th of a 30-day period → new end is 15th + 30 = 45th, but tenant paid until the 30th → 15 days lost.

## Severity
🟡 Medium

## Proposed Plan

### 1. Root Cause Analysis
The root issue is not just the `+30 days` arithmetic — it is the absence of any check against the existing `current_period_end` before overwriting it. The `WebhookLog` idempotency check on `paypal-transmission-id` prevents exact duplicates, but PayPal can fire two *different* transmission IDs for the same billing cycle under certain retry conditions.

### 2. Fix Applied by Claude Code
```javascript
// FIXED — extend from the later of current_period_end or now
const now = new Date();
const base = tenant.current_period_end && tenant.current_period_end > now
    ? tenant.current_period_end
    : now;
const newPeriodEnd = new Date(base);
newPeriodEnd.setDate(newPeriodEnd.getDate() + 30);
```

## Resolution of Sub-Questions

### Sub-question A — Does 3.4's `next_billing_date` approach supersede the current fix? ✅
**Yes, and it is already applied.** The current `handlePaymentCompleted` (lines 124–148) checks
`resource.next_billing_date` first, then `resource.billing_info.next_billing_time`, then falls back
to calendar-aware `setMonth(+1)` with `billing_cycle_anchor` snap-back. The plain `+30 days` is
entirely gone. Audit 3.4 and 3.8 fixes are both present in production code.

### Sub-question B — Is `Payment.transaction_id` uniquely constrained? ✅
**Yes.** `backend/src/models/Landlord/Payment.js` line 24 declares `unique: true` on
`transaction_id`. The same constraint appears in migration
`20260210000001-add-subscription-schema.cjs`. A second webhook carrying the same `transaction_id`
but a different `paypal-transmission-id` will hit a database-level duplicate error before
inserting a second `Payment` row. No additional guard is needed.

### Sub-question C — Does forward-extending `current_period_end` break the grace period logic? ✅
**No.** `billingScheduler.checkExpiredSubscriptions()` queries tenants where
`current_period_end < now`. Correctly extending this date forward only delays when a tenant
enters the expiry query — which is the desired behavior. Tenants whose period genuinely lapses
still enter the grace period (`subscription_status = 'past_due'`, `grace_period_end = now + 3 days`)
and are hard-downgraded after that window. No scheduler logic is affected.

### Sub-question D — Is `setDate(+30)` calendar-safe? ✅ (moot — code now uses `setMonth`)
The old `setDate(+30)` had month-boundary drift (e.g., Jan 31 + 30 days = Mar 2 instead of Feb 28).
The current fallback uses `setMonth(getMonth() + 1)` with overflow protection (`setDate(0)` snaps
back to the last valid day of the target month) and `billing_cycle_anchor` alignment. This is
calendar-correct. The DST concern from 3.2 does not apply because `setMonth` is UTC-calendar-aware
in V8 when operating on local Date objects within a server process with a fixed timezone.

### Sub-question E — Missing test 1d ✅ ADDED
Test `1d` was absent from `paypalWebhookHandlers.test.js` despite the audit referencing "1a–1d."
It has been added: it passes `next_billing_date` in the PayPal resource and asserts that
`tenant.current_period_end` is set to exactly that value (the authoritative PayPal path), not the
calendar fallback. This makes the 3.4 integration verifiable in CI.
