# Audit 3.8 - Payment webhook period-end reset on duplicate or delayed events

## Status
Resolved

## Severity
Unspecified

## Root Cause
A delayed or duplicated `PAYMENT.SALE.COMPLETED` event could previously cause billing-window drift or backward subscription period movement if period-end mutation was not monotonic.

## Fix Implemented
1. Webhook event id is the primary dedupe key.
- Dedupe key now prefers PayPal `event.id`; `paypal-transmission-id` is fallback only.
- Evidence:
  - `backend/src/controllers/paymentController.js` (`buildWebhookDedupKey`, around lines 21-25)
  - webhook idempotency check (`WebhookLog.findOne/findOrCreate`, around lines 69-84)

2. Duplicate `transaction_id` is blocked at DB layer.
- `payments.transaction_id` is unique.
- Duplicate insert path is handled as idempotent success (no tenant mutation).
- Evidence:
  - `backend/src/models/Landlord/Payment.js` (around lines 21-25)
  - `backend/migrations/20260210000001-add-subscription-schema.cjs` (around lines 69-73)
  - `backend/src/controllers/paymentController.js` (around lines 152-166)

3. Period-end calculation uses authoritative PayPal billing timestamp first.
- Prefers `resource.next_billing_date` then `resource.billing_info.next_billing_time`.
- Fallback is calendar-aware one-month extension using anchor-day snap-back.
- Evidence: `backend/src/controllers/paymentController.js` (around lines 171-188).

4. Period-end is monotonic and never moves backward.
- Final `nextBillingDate` is guarded by `maxDate(nextBillingDate, current_period_end)`.
- Evidence: `backend/src/controllers/paymentController.js` (around lines 190-193).

5. Anchor consistency is preserved.
- Authoritative dates refresh `billing_cycle_anchor` from date-of-month.
- Fallback path initializes anchor when missing.
- Evidence: `backend/src/controllers/paymentController.js` (around lines 199-204).

## Test Evidence
Primary regression suite:
- `backend/tests/paypalWebhookHandlers.test.js`

Covered scenarios include:
- first payment period initialization
- duplicate/late webhook does not regress period end
- authoritative `next_billing_date` path
- authoritative older date does not move period backward
- duplicate `transaction_id` handled as idempotent success
- webhook dedupe uses event id when present
