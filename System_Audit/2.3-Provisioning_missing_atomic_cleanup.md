# Audit Finding 2.3 — Provisioning flow lacks atomic cleanup on failure

## Status: ✅ RESOLVED (Phase 35 — 2026-02-17)

---

## User Feedback
> Alright, we need an atomic cleanup on failure to remove bloating and unnecessary storage and quota

## Finding Description
If `provisionTenant` fails after creating the database but before seeding, the `catch` block updates status to 'failed' but does **not** drop the partially created database.

## Severity
🟡 Medium

---

## Root Cause
In `backend/src/services/tenantProvisioningService.js`, the `provisionTenant` function sequentially performs:

1. Tenant Record Create (Sequelize transaction — rolls back cleanly on failure)
2. `CREATE DATABASE` — **non-transactional DDL, cannot be rolled back**
3. `sequelize.sync` — schema creation
4. Seed Admin User
5. Update Tenant status to `'active'`

If steps 3, 4, or 5 throw, the original catch block called `Tenant.update({ status: 'failed' })` but did **not** drop the database created at step 2. This left a "zombie" `sku_tenant_*` database behind.

---

## Fix Applied

**File**: `backend/src/services/tenantProvisioningService.js` (catch block, lines 158–181)

The catch block was extended with a two-step compensating transaction:

```javascript
} catch (error) {
    logger.error(`[Provisioning] Error: ${error.message}`);

    // 1. Mark tenant record as failed
    try {
        const Tenant = dbStore.get('Tenant');
        await Tenant.update({ status: 'failed' }, { where: { id: uuid } });
    } catch (cleanupError) {
        logger.warn(`[Provisioning] Failed to mark tenant as failed: ${cleanupError.message}`);
    }

    // 2. Drop the zombie database (compensating transaction)
    if (dbName && dbName.startsWith('sku_tenant_')) {
        try {
            await deleteTenantDatabase(dbName);
            logger.info(`[Provisioning] Zombie database ${dbName} dropped during cleanup`);
        } catch (dropError) {
            logger.error(`[Provisioning] CRITICAL: Failed to drop zombie database ${dbName}: ${dropError.message}`);
        }
    }

    throw error;
}
```

**Safety**: `deleteTenantDatabase` already enforces `dbName.startsWith('sku_tenant_')` internally. The additional inline guard is belt-and-suspenders. Drop errors are logged at CRITICAL but not re-thrown — the original provisioning error always propagates to the caller.

---

## Verification

Automated tests added in `backend/tests/tenantProvisioning.test.js`:

| Test | Failure Mode | Result |
|------|---|---|
| 1 | `sequelize.sync` throws | Error propagates · tenant marked `failed` · `DROP DATABASE` issued ✅ |
| 2 | Sync throws + status-update also throws (double-fault) | Original error propagates · DROP still runs ✅ |

Both tests run against the real MySQL instance — actual `CREATE DATABASE` and `DROP DATABASE IF EXISTS` queries were confirmed in logs.

Run with:
```bash
cd backend && npm test -- tests/tenantProvisioning.test.js
```

---

## Scope Note
This fix covers the `provisionTenant` service-level catch block, which fires for all three call paths:
- Premium auto-provisioning on company registration
- Admin manual approval of a pending tenant
- Legacy direct provisioning endpoint

A separate gap exists at the controller level (Call Path 1): the Tenant record is created with `status: 'active'` in the controller *before* `provisionTenant` is called. If provisioning fails, the record is corrected to `'failed'` by the service-level catch, but this is not covered by a system audit finding at this time.
