# Implementation Plan - 6.2 CSV Formula Injection (CSV Injection)

## User Feedback
> Secure the CSV Formula Injection to make sure that there wouldn't be bypassers using special characters

## Finding Description
The export functionality does not sanitize fields starting with special characters (`=`, `+`, `-`, `@`), risking formula injection attacks.

## Severity
🟠 High

## Proposed Plan

### 1. Root Cause Analysis
In `backend/src/services/csvImportService.js`:
- The `transformRow` function (Lines 33+) maps CSV columns to `item` properties.
- **Code**:
    ```javascript
    if (row.description) item.description = row.description.trim();
    ```
- **Vulnerability**: It does not check if the string starts with malicious characters (`=`, `+`, `-`, `@`).
- **Scenario**:
    - Attacker uploads a CSV with Item Name: `=cmd|' /C calc'!A0`.
    - Data is saved to DB.
    - Admin exports "All Items" to CSV/Excel.
    - Admin opens the file in Excel.
    - Excel executes the formula (populates calculator).

### 2. Proposed Changes
Sanitize all string inputs during import.

#### A. Create Sanitization Helper
Add a helper function to escape dangerous characters.

```javascript
/* csvImportService.js */
const sanitizeForSpreadsheet = (val) => {
    if (typeof val !== 'string') return val;
    const dangerousPrefixes = ['=', '+', '-', '@'];
    const trimmed = val.trim();
    if (dangerousPrefixes.some(prefix => trimmed.startsWith(prefix))) {
        return `'${trimmed}`; // Prepend single quote to force text interpretation
    }
    return trimmed;
};
```

#### B. Apply inside `transformRow`
Apply this to all text-based fields (`sku_code`, `name`, `description`, `production_notes`, `category`, etc.).

```javascript
/* Inside transformRow */
if (row.sku_code) item.sku_code = sanitizeForSpreadsheet(row.sku_code);
if (row.name) item.name = sanitizeForSpreadsheet(row.name);
// ... repeat for all string fields
```

### 3. Verification Plan

#### Automated Test
1.  Upload CSV with field starting with `=SUM(1+1)`.
2.  Check Database.
3.  **Expect**: Database value should be `'=SUM(1+1)` (with leading quote) OR just ensure the API returns it safely.
4.  **Note**: The goal is to prevent *Execution*. Saving the quote is the standard mitigation.

### 4. Risk Assessment
- **Impact**: Low (Client-Side Security for Admins).
- **Side Effect**: The leading quote will appear in the UI (`'Product Name`). This is ugly but necessary.
    - *Refinement*: Alternatively, we can strip the invalid start character if it's not needed, but that alters data. The single quote is the standard OWASP recommendation.
    - *UI Adjustment*: The Frontend can strip the leading single quote if needed for display, but that adds complexity. We will stick to saving the safe version.
