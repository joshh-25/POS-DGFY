# Implementation Plan - 8.2 In-Memory State Usage (Clustering/Scaling Issue)

## User Feedback
> Design an implementation plan that will address this project's scalability

## Finding Description
`tempFileService` uses a local In-Memory `Map` to store references to generated CSV files, breaking horizontal scaling.

## Severity
🟡 Medium

## Proposed Plan

### 1. Root Cause Analysis
In `backend/src/schedulers/billingScheduler.js`:
- The `initBillingScheduler` function starts a standard `node-cron` job.
- **Vulnerability**: The scheduler runs locally on *every* instance of the backend.
- **Scenario**:
    - Production environment scales to 3 instances (for high availability).
    - At midnight, all 3 instances wake up.
    - All 3 instances query the DB for expiring subscriptions.
    - All 3 instances send emails.
    - Result: Users receive 3x "Subscription Expiring" emails. If auto-charge logic existed, they would be triple-charged.
- **Analysis**: Code assumes a single-server deployment.

### 2. Proposed Changes
Implement Distributed Locking using Redis (Redlock pattern or `setNx`).

#### A. Modify `billingScheduler.js`
1.  Wrap the job execution in a Redis Lock check.
2.  Key: `scheduler:lock:billing_daily`. TTL: 5 minutes.
3.  If `setNx(key, uuid)` returns false (locked), skip execution.

```javascript
/* billingScheduler.js */
import { getRedisClient } from '../config/redis.js';

cron.schedule('0 0 * * *', async () => {
    const client = getRedisClient();
    // Simple Lock: Set if not exists, expire in 10 mins
    const acquired = await client.set('scheduler:lock:billing_daily', 'locked', {
        NX: true,
        EX: 600
    });

    if (!acquired) {
        logger.info('Billing scheduler: Lock held by another instance. Skipping.');
        return;
    }

    try {
        await checkExpiringSubscriptions();
        // ...
    } catch (e) {
        // ...
    } finally {
        // Optional: Release lock, or let it expire (safer for cron to let exp)
    }
});
```

### 3. Verification Plan

#### Manual Verification
1.  Start 2 backend processes locally (different ports).
2.  Trigger the scheduler manually (or wait).
3.  **Expect**: Only one process logs "Sending expiry warning". The other logs "Lock held...".

### 4. Risk Assessment
- **Impact**: High (prevents spam/double-billing in scaled env).
- **Complexity**: Low (standard Redis pattern).
