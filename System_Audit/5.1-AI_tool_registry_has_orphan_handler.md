# [OPEN] 5.1 AI Tool Registry Has Orphan Handler

Severity: Medium
Audit area: AI tooling, registry integrity

## Re-Baseline Update (2026-08-05)

**Still open, unchanged.** `get_job_order_details` still has a live handler (`backend/src/modules/ai/usecases/toolHandlers/jobOrderToolRegistry.js:166`), is still wired into `toolRegistryMap.js:171`, and is still dispatched from `executeAiToolUseCase.js:53` — with no matching definition in `backend/src/config/aiTools.js`. The only non-test caller found is `backend/scripts/qa_30_questions_verification.js:160`, which is likely why it was never removed — this leans the "deprecated vs. active" question toward "QA-script-only, no governed tool definition." Separately, `npm run validate:ai` currently cannot run in a fresh checkout (`Cannot find package '@sieitzz/shared-constants'`), which blocks the re-run this finding's remediation item 3 asks for until workspace deps are linked.

## Finding

The AI registry validation passed with a warning for one orphan handler.

## Evidence

- `npm run ai:check` passed.
- The command reported 66 tool definitions and 67 handlers.
- The command warned about orphan handler `get_job_order_details`.

## Why This Matters

AI tool registries should be deterministic. Orphan handlers can indicate stale implementation, undocumented capability, drift between tool definitions and runtime handlers, or incomplete governance over what the assistant can call.

## Required Remediation

1. Determine whether `get_job_order_details` is deprecated or missing a tool definition.
2. Remove it if unused, or add the governed tool definition and tests if it is active.
3. Re-run `npm run ai:check`.
4. Commit regenerated AI capability documentation only if it reflects intentional state.

## Acceptance Gates

- AI validation passes without orphan-handler warnings.
- Tool definitions and handlers have one-to-one intentional mapping.
- AI capability docs match runtime behavior.
