# Audit 3.7 — Subscription activation webhook never sets plan to premium

## Status
✅ **FULLY RESOLVED** in Phase 40. All three gaps identified in this issue are closed.

---

## Original Finding

`handleSubscriptionActivated` in `paymentController.js` only set `subscription_status`:

```javascript
// BROKEN — before fix
tenant.subscription_status = 'active';
await tenant.save();
```

The access gate in `backend/src/middleware/auth.js` only checks `plan`, not `subscription_status`:

```javascript
export const requirePremium = (req, res, next) => {
    if (req.tenant.plan === 'premium') return next(); // Only checks plan
    return res.status(403).json({ ... requiresUpgrade: true });
};
```

If `plan` was never set to `'premium'`, the tenant is blocked regardless of `subscription_status`.

## Severity
🔴 Critical (Gap 2) / 🟡 Moderate (Gaps 3 & 4)

## Root Cause

PayPal fires two events for a new subscription in unpredictable order:
1. `BILLING.SUBSCRIPTION.ACTIVATED` — subscription exists and is active
2. `PAYMENT.SALE.COMPLETED` — first payment cleared

If event (1) arrived before event (2), the tenant was stuck with `plan: 'standard'` until the next
payment event arrived. Because both handlers failed to set `plan`, even the second event would not
recover the account via the webhook path.

## Gaps Identified & Resolved

### Gap 2 — `handleSubscriptionActivated` never set `plan = 'premium'` ✅ RESOLVED
**File**: `backend/src/controllers/paymentController.js` lines 173–174

```javascript
// FIXED
tenant.plan = 'premium';
tenant.subscription_status = 'active';
```

### Gap 3 — `handleSubscriptionCancelled` never set `cancelled_at` ✅ RESOLVED
**File**: `backend/src/controllers/paymentController.js` line 196

The `cancelSubscription` API endpoint (user-initiated path) already set `cancelled_at: new Date()`.
The webhook handler (PayPal-portal cancellation path) did not — creating a silent inconsistency
where the audit timestamp was missing for externally-triggered cancellations.

```javascript
// FIXED
tenant.subscription_status = 'cancelled';
tenant.cancelled_at = new Date();
// Access is not immediately revoked — billingScheduler will downgrade
// plan to 'standard' after current_period_end passes the grace window.
await tenant.save();
```

**Design decision**: `plan` is intentionally NOT changed here. `billingScheduler.checkExpiredSubscriptions()`
owns the downgrade (`plan = 'standard'`, `subscription_status = 'inactive'`) after `current_period_end`
plus the 3-day grace period. Setting `plan` in the webhook handler would bypass that grace period.

### Gap 4 — `syncWithPayPal` never updated the `plan` field ✅ RESOLVED
**File**: `backend/src/controllers/paymentController.js` lines 308–310

`syncWithPayPal` is the self-healing endpoint a tenant calls when their account state looks wrong.
It was updating `subscription_status` but not `plan` — meaning a tenant whose `plan` had drifted
to `'standard'` would still fail `requirePremium` even after a successful sync showing `ACTIVE`.

```javascript
// FIXED — only upgrade plan on confirmed ACTIVE; never downgrade here
if (details.status === 'ACTIVE') {
    updatePayload.plan = 'premium';
}
```

Non-ACTIVE statuses (CANCELLED, SUSPENDED, EXPIRED) do not downgrade `plan` — that is deferred
to `billingScheduler` to preserve the 3-day grace period.

## State Machine Reference

The authoritative subscription state machine, as implemented in `billingScheduler.js`:

| State | `plan` | `subscription_status` | Who sets it |
|-------|--------|----------------------|------------|
| Active subscriber | `premium` | `active` | webhook / upgrade endpoint |
| Cancelled (waiting for period end) | `premium` | `cancelled` | `handleSubscriptionCancelled` / `cancelSubscription` endpoint |
| Expired → grace period | `premium` | `past_due` | `billingScheduler` |
| Hard downgrade | `standard` | `inactive` | `billingScheduler` only |
