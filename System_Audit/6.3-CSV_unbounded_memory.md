# Implementation Plan - 6.3 Unbounded Memory Usage (DoS Risk)

## User Feedback
> Prevent application crashes by figuring out how to intellgiently house the large files. In the future, just letting you know, I will make a storage for large files

## Finding Description
The controller buffers the entire uploaded file into memory (`req.file.buffer.toString()`) before processing.

## Severity
🟡 Medium

## Proposed Plan

### 1. Root Cause Analysis
- **Layer 1 (Upload)**: `backend/src/config/uploadConfig.js` uses `multer.memoryStorage()`.
    - **Issue**: The entire file provided by the user is buffered into RAM *before* the controller even sees it. A 50MB file = 50MB Buffer in RAM. 100 concurrent uploads = 5GB RAM. Node.js crashes.
- **Layer 2 (Processing)**: `backend/src/services/csvImportService.js` uses `csv-parse/sync`.
    - **Issue**: Converting that 50MB buffer to a string and synchronously parsing it creates massive GC pressure and blocks the Event Loop (CPU freeze) for seconds.

### 2. Proposed Changes
Switch to Streaming for both Upload and Parsing.

#### A. Modify `uploadConfig.js`
Use `multer.diskStorage` (or stream directly if possible, but disk is safer for temp handling) instead of `memoryStorage`.

```javascript
/* uploadConfig.js */
const storage = multer.diskStorage({
    destination: (req, file, cb) => cb(null, os.tmpdir()),
    filename: (req, file, cb) => cb(null, `${Date.now()}-${file.originalname}`)
});
```

#### B. Modify `csvImportService.js`
Accept a *filePath* instead of string content. Use `fs.createReadStream` and `csv-parse` stream API.

```javascript
/* csvImportService.js */
import fs from 'fs';
import { parse } from 'csv-parse';

export const processCsvStream = (filePath) => {
    return new Promise((resolve, reject) => {
        const parser = fs.createReadStream(filePath).pipe(parse({
            columns: true,
            trim: true
        }));
        
        parser.on('readable', async () => {
             // Process in chunks or batch insert here
             // Ideally: Read 100 -> Pause Stream -> Insert DB -> Resume Stream
        });
        
        // ... (Full stream logic replaces synchronous parse)
    });
};
```

**Note**: Since a full refactor to Streams is complex, valid *mitigation* for this Audit Task is to Enforce strict file size limits (e.g. 5MB) in `uploadConfig` and keep the sync logic, accepting the limitation.
**Decision**: Given this is an existing system, switching to Streams is a *Refactor*. The *Fix* for the Vulnerability is strictly enforcing size limits if we keep memory storage.
**Revised Plan**:
1.  Enforce 2MB limit in `uploadConfig` (currently 10MB, which is risky for Sync).
2.  Switch to `diskStorage` to avoid RAM spikes for the buffer itself.
3.  Modify Service to read from Disk (fs.readFileSync) if sticking to Sync, OR refactor to Stream.
    - *Recommendation*: **Refactor to Stream** is the only "Secure" way for "Unbounded" memory.
    - *Compromise*: For this plan, we will detail the **Stream Refactor**.

### 3. Verification Plan

#### Automated Test
1.  Generate a 50MB Random CSV.
2.  Upload it.
3.  **Expect**: 
    - **Current**: Server RAM spikes + Event Loop Lag (detected by health check ping timeout).
    - **Fixed**: RAM stays flat, Event Loop remains responsive.

### 4. Risk Assessment
- **Impact**: High (DoS).
- **Effort**: High (Refactoring Sync logic to Async Stream logic).
- **Backwards Compatibility**: The Service signature changes (`process(content)` -> `process(filePath)`). Controllers must be updated.
