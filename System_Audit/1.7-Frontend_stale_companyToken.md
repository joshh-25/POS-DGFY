# [FIXED] 1.7 Frontend doesn't clear `companyToken` on failed refresh

## User Feedback
> You know what to do ;) ezpz

## Finding Description
When token refresh fails, the interceptor clears `authToken` and `refreshToken` from localStorage but does **not** clear `companyToken`.

## Severity
🟢 Low

## Proposed Plan

### 1. Root Cause Analysis
In `frontend/src/services/api.js`, the request interceptor attaches the `x-company-token` header from `localStorage` if it exists.
In `frontend/src/services/authService.js`, the `companyToken` is set during login/register but persisted indefinitely.
- **Problem**: If a user is removed from a company or their access is revoked, the frontend still sends the old `companyToken`. Middleware on the backend might validate it, but the frontend UI remains in a "stale" state, trying to access a tenant it no longer has access to, often resulting in confusing 403/404 errors instead of a clean logout or context switch.

### 2. Proposed Changes
We need to ensure the `companyToken` state is synchronized with the user's current valid session.

#### A. Validate Company Token on App Init
In `App.jsx` or a dedicated `AuthContext` initialization:
1.  Check if `companyToken` exists.
2.  Call a new endpoint or existing `validate-token` endpoint.
3.  If invalid/expired, clear it from `localStorage` and redirect to "Select Company" or "Login" screen.

#### B. Clear Token on 401/403
Update the Response Interceptor in `frontend/src/services/api.js`:
- Current logic handles `401` by trying refresh.
- **Add**: If refresh fails OR if we receive a specific "Invalid Company Token" error (e.g., 403/404 on tenant check), explicitly `localStorage.removeItem('companyToken')`.

```javascript
// frontend/src/services/api.js

api.interceptors.response.use(
  (response) => response,
  async (error) => {
    // ... existing 401 logic ...
    
    // NEW: Handle stale tenant context
    if (error.response?.status === 404 && error.response?.data?.message?.includes('Tenant')) {
       // Tenant no longer exists or user removed
       localStorage.removeItem('companyToken');
       window.location.href = '/login'; 
    }
    
    return Promise.reject(error);
  }
);
```

#### C. Enhanced Logout
Ensure `authService.logout()` clears ALL related items. (Already verified in `authService.js` line 61: `localStorage.removeItem('companyToken')` exists, so this part is good).

### 3. Verification Plan

#### Automated Test (Frontend E2E)
1.  Login and set a valid `companyToken`.
2.  Manually tamper `localStorage` to set an invalid `companyToken`.
3.  Refresh page.
4.  **Expect**: App detects invalid token and redirects to setup/login, clearing the storage.

#### Manual Verification
1.  Log in.
2.  Backend: Manually delete the tenant or user-tenant mapping.
3.  Frontend: Click a navigation link.
4.  **Expect**: 404/403 error caught by interceptor -> user redirected to login -> `companyToken` cleared.

### 4. Risk Assessment
- **Impact**: Low. Improves UX reliability.
- **Mitigation**: Ensure we don't clear the token on transient network errors, only on definitive "Invalid Tenant" responses.

### 5. Files to Change
- `frontend/src/services/api.js`
- `frontend/src/App.jsx` (or AuthProvider)
