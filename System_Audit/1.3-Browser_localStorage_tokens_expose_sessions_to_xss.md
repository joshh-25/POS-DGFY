# [REMEDIATED] 1.3 Browser localStorage Tokens Expose Sessions to XSS

Severity: High
Audit area: Session management, frontend security

## Finding

Multiple frontend paths persist authentication, refresh, DGFY, or storefront tokens in `localStorage`.

## Evidence

Static scan found token persistence in:

- `frontend/src/main.jsx`
- `frontend/src/services/authService.js`
- `frontend/src/services/api.js`
- `frontend/src/services/dgfyAuthService.js`
- `frontend/apps/store/src/StorefrontApp.jsx`

`frontend/src/main.jsx` also includes development auto-login behavior that writes local auth and refresh tokens.

Implementation evidence captured on 2026-06-02 and tightened on 2026-06-03:

- `backend/src/utils/browserSessionCookies.js` centralizes HttpOnly session cookies, tenant context cookies, CSRF cookies, and clearing behavior.
- `backend/src/middleware/csrfProtection.js` requires `x-csrf-token` for cookie-authenticated unsafe requests.
- `backend/src/modules/auth/controllers/authHandlers.js` sets tenant refresh/session cookies and no longer returns browser refresh tokens in login, refresh, or invitation acceptance JSON.
- `/api/v1/auth/refresh-token` uses the tenant refresh cookie as browser refresh authority and rejects body-only refresh token authority.
- `backend/src/middleware/dgfyAuth.js`, `backend/src/modules/dgfy/controllers/dgfyAuthHandlers.js`, `backend/src/middleware/storeAuth.js`, `backend/src/modules/store/controllers/storeHandlers.js`, and `backend/src/modules/adminAuth/controllers/adminAuthHandlers.js` support cookie-backed DGFY, storefront, and admin sessions.
- `frontend/src/services/browserSession.js` stores tenant access tokens only in module memory and reads CSRF from the browser-readable CSRF cookie.
- `frontend/src/services/authService.js`, `frontend/src/services/api.js`, `frontend/src/services/dgfyAuthService.js`, `frontend/src/services/adminService.js`, `frontend/src/main.jsx`, `frontend/Pages/AcceptInvite.jsx`, and storefront auth helpers no longer persist privileged tokens in browser-readable storage.
- `docs/architecture/adr/0026-browser-session-cookie-authority.md` records the cross-boundary browser session contract.
- `backend/tests/rtr_verification.test.js` proves cookie attributes, CSRF enforcement, refresh-cookie rotation, replay rejection, rotated-cookie success, and body-only refresh-token rejection.

## Why This Matters

Tokens in `localStorage` are readable by any successful script execution in the page. This turns XSS from page compromise into session theft. The risk is amplified because the app has administrative, tenant, POS, storefront, and DGFY surfaces.

## Required Remediation

1. Move refresh/session authority to `HttpOnly`, `Secure`, `SameSite` cookies where feasible.
2. Keep access tokens short-lived and rotate refresh tokens.
3. Remove long-lived privileged tokens from browser-readable storage.
4. Add CSP, XSS regression tests, and token lifecycle tests.
5. Ensure development auto-login cannot be included in production builds.

## Acceptance Gates

- No long-lived refresh token is stored in `localStorage`.
- Refresh authority is not accepted from browser JSON request bodies.
- Production build cannot enable dev auto-login.
- Session renewal and logout are covered by tests.
- XSS smoke tests prove injected script cannot read refresh authority.
