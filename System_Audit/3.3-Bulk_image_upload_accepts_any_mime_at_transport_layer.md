# [RESOLVED] 3.3 Bulk Image Upload Accepts Any MIME at Transport Layer

Severity: High (contract clarified and covered)
Audit area: File upload security, resource abuse

## Finding

The bulk catalog image upload transport filter accepts any MIME type before deeper validation occurs. That behavior is now documented as intentional for bulk POS and Storefront catalog setup because ADR 0017 requires per-file partial-success results instead of whole-batch transport rejection.

## Evidence

- `backend/src/config/uploadConfig.js` keeps bulk POS and Storefront catalog uploads lenient at multer while pinning transport caps to 50 files and 6 MB per temporary file.
- `backend/src/modules/pos/usecases/posUseCases.js` and `backend/src/modules/inventory/usecases/storefrontCatalogUseCases.js` validate each uploaded temp file before persistence using the shared MIME allowlist and binary signature validator.
- Single-image and gallery upload middleware remains transport-strict because those endpoints are all-or-nothing.

## Why This Matters

Bulk catalog setup has two competing requirements: reject unsafe content before storage, and return actionable per-file results for mixed batches. The governed contract keeps the batch parse lenient only long enough to classify each file. Unsupported MIME, unsupported signatures, MIME/signature mismatches, product-policy oversize files, duplicate filenames, unmatched SKU stems, readiness blockers, and write failures are returned per file, and rejected temp files are removed best-effort.

## Remediation

1. Keep the ADR 0017 bulk contract: lenient transport, strict per-file use-case validation.
2. Validate reported MIME and magic bytes before `imageStorage.store`.
3. Reject MIME/signature mismatches and unsupported signatures before persistence.
4. Enforce the 5 MB product image policy per result row while retaining the 6 MB transport temp cap.
5. Clean rejected temp files and remove newly stored files when catalog writes fail.
6. Cover invalid MIME, spoofed signature, oversize, mixed valid/invalid batch, failed-write cleanup, and transport-cap expectations with regression tests.

## Acceptance Gates

- Bulk image upload rejects non-image content before image persistence.
- Spoofed extension or mismatched magic bytes are rejected per file.
- Rejected temp files are cleaned after rejection.
- Newly stored files are removed when the catalog write fails.
- Transport DoS limits are covered by tests.
- Docs identify why bulk transport differs from strict single-image upload.
