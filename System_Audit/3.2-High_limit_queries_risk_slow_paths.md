## Finding

Several backend paths request high result limits that can create slow queries, high memory use, or large response payloads under production data volume.

## Evidence

Static scan found examples including:

- `backend/src/services/dispatchOrderService.js` using `limit: 10000`.
- `backend/src/services/stockMovementService.js` using `limit: 10000`.
- `backend/src/modules/pos/usecases/posUseCases.js` using `limit: 5000`.
- `backend/src/modules/services/repositories/serviceRepository.js` using `limit: 2000`.

## Why This Matters

Large unpaginated reads become operational incidents as tenant data grows. They can increase database load, slow API responses, increase memory pressure, and degrade POS/storefront/admin workflows.

## Required Remediation

1. Review each high-limit path for user workflow and data-volume assumptions.
2. Replace large reads with pagination, cursoring, streaming export, or bounded aggregate queries.
3. Add database indexes where query plans require them.
4. Add performance tests or query-plan evidence for high-volume tenant data.

## Acceptance Gates

- High-limit reads are either removed, paginated, or documented as bounded by business rules.
- Export-style workflows use streaming or async jobs.
- API tests cover max-page and over-limit behavior.
