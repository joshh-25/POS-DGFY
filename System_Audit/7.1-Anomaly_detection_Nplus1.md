# ? RESOLVED - Implementation Plan - 7.1 N+1 Query & Inefficient Data Processing in Anomaly Detection

## User Feedback
> Let us effectively use database aggregations

## Finding Description
`detectAnomalies` loops through every item triggering individual queries and fetches all records into memory instead of using DB aggregations.

## Severity
🟠 High

## Proposed Plan

### 1. Root Cause Analysis
In `backend/src/services/analyticsService.js`, the `detectAnomalies` function (Lines 169-278) exhibits a classic N+1 query performance vulnerability.
- **Code**:
    ```javascript
    // 1. Fetch relevant items (Query 1)
    const items = await Item.findAll({ ... });

    for (const item of items) {
        // 2. Fetch movements for this item (Query N)
        const movements = await StockMovement.findAll({
            where: { item_id: item.item_id, ... }
        });
        // ... processing ...
    }
    ```
- **Impact**: If there are 1,000 items, this endpoint executes 1,001 database queries. This will cause the "Anomalies" dashboard widget to time out or crash the database connection pool under load.

### 2. Proposed Changes
Refactor to use Batch Fetching (2 Queries Total).

#### A. Modify `detectAnomalies`
1.  Fetch Items.
2.  Extract all `item_id`s.
3.  Fetch *all* relevant StockMovements for these IDs in one query.
4.  Group movements by `item_id` in memory using a Map/Object.
5.  Iterate items and lookup movements from the Map.

```javascript
/* analyticsService.js */
export const detectAnomalies = async (options = {}) => {
    // ... setup (lines 169-180) ...

    // 1. Fetch relevant items
    const items = await Item.findAll({ ... });
    if (items.length === 0) return [];

    const itemIds = items.map(i => i.item_id);

    // 2. Batch Fetch Movements (Single Query)
    const allMovements = await StockMovement.findAll({
        where: {
            item_id: { [Op.in]: itemIds },
            timestamp: { [Op.gte]: startDate }
        },
        order: [['timestamp', 'ASC']]
        // Optimize: attributes: ['movement_id', 'item_id', 'quantity', 'movement_type', 'timestamp']
    });

    // 3. Group by Item ID
    const movementsMap = {}; // Record<itemId, StockMovement[]>
    for (const m of allMovements) {
        if (!movementsMap[m.item_id]) movementsMap[m.item_id] = [];
        movementsMap[m.item_id].push(m);
    }

    const anomalies = [];

    // 4. Process In-Memory
    for (const item of items) {
        const movements = movementsMap[item.item_id] || [];
        // ... (Existing anomaly detection logic: check losses, spikes code unchanged) ...
    }

    return anomalies.sort(...);
};
```

### 4. Risk Assessment
- **Impact**: High (Performance/DoS).
- **Memory**: Fetching *all* movements for all items might check 10k+ rows.
    - *Mitigation*: The `options` usually filter by Category. If filtering is null (All Items), we might hit memory limits.
    - *Refinement*: If `items.length` > 500, we should process in chunks (e.g., chunk items into groups of 100, fetch movements for that chunk, process, repeat). For this plan, the Batch Fetch is the primary fix for the N+1. Pagination/Chunking is a secondary optimization.
