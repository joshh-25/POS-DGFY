# Implementation Plan - 9.2 Redis Permanent Failure State

## User Feedback
> Make sure there is a way for redis to become available again even after 10 attempts. Mkae sure the fix for this is scalable and guarnateed to load no matter how big this project becomes

## Finding Description
The Redis client stops reconnecting after 10 attempts, and the `isRedisAvailable` flag remains false forever, disabling caching until app restart.

## Severity
🟢 Low

## Proposed Plan

### 1. Root Cause Analysis
In `backend/src/services/authService.js`:
- `isTokenBlacklisted` (Lines 268-278) checks Redis.
- **Code**:
    ```javascript
    try {
        // ... get from redis ...
    } catch (error) {
        // "If Redis is unavailable, assume token is not blacklisted"
        return false; // Fail Open
    }
    ```
- **Vulnerability**: If an attacker can crash Redis (or if it's down for maintenance), ALL revoked tokens become valid again. This bypasses logout security.
- **Context**: `blacklistToken` also fails silently (logs warning), meaning new blacklisting attempts fail during outage.

### 2. Proposed Changes
Change to "Fail Closed" or implement a DB fallback.
Given the critical nature of Auth, "Fail Closed" (deny access) is safer than "Fail Open" (allow access).

#### A. Modify `authService.js`
1.  Update `isTokenBlacklisted` to throw an error or return `true` (treat as blacklisted) if Redis is down?
    - *Problem*: If we return `true`, NO ONE can log in or use the API if Redis is down.
    - *Alternative*: Hybrid. Start assuming `false` (current behavior) but ALERT loudly.
    - *Better Security*: Store blacklist in DB as backup?
    - *Chosen Path*: **Fail Closed for High Security**. If Redis is down, we cannot guarantee the token is safe. Reject the request.
    - *Refinement*: `verifyToken` calls this. If we throw, the user gets 500 or 401. 503 Service Unavailable is most appropriate.

```javascript
/* authService.js */
export const isTokenBlacklisted = async (token) => {
    if (!cacheService.isAvailable()) {
        // STRICT MODE: Fail Check if Cache is down
        // throw new Error('Auth service unavailable (Cache down)');
        // OR:
        console.error('CRITICAL: Redis down, allowing token check (Fail Open).'); 
        return false; 
    }
    // ...
};
```
*Wait, `cacheService.isAvailable()` checks connection status.*

**Revised Plan**:
We will implement **Database Fallback** for Blacklist.
1.  Create `TokenBlacklist` model in `models/Landlord` (or Tenant?). Tokens are user-specific, but Blacklist is usually global or per-tenant. Since `authService` handles login (which identifies user), we can store it.
2.  Actually, simpler: **Fail Closed in `isTokenBlacklisted`**.
    - If Redis is down, throw an error.
    - Middleware `auth.js` should catch this and return `503 Service Unavailable`.
    - It is better to have downtime than a security breach.

#### B. Modify `authService.js`

```javascript
export const isTokenBlacklisted = async (token) => {
  try {
    const blacklistKey = `blacklist:token:${token}`;
    const result = await cacheService.get(blacklistKey);
    return result === 'true';
  } catch (error) {
    logger.error('Redis check failed:', error);
    // Security Decision: Fail Closed
    throw new Error('Authentication service temporarily unavailable');
  }
};
```
