# System Audit - 2.1 Memory leak in `tenantHandler` - [FIXED]

## Status
Resolved

## Severity
Critical

## Root Cause
`tenantHandler` called `getTenantModels(sequelizeInstance)` on **every single request**, executing `sequelize.define()` for ~30 models each time, creating new Model classes in memory and leaking Sequelize internal metadata.

## Fix Implemented
1.  **Model Caching**: Implemented a check in `tenantModelFactory.js` to skip re-definition if models already exist on the `Sequelize` instance.
2.  **Initialization Guard**: Added `_tenantModelsInitialized` flag to ensure association logic only runs once per tenant.
3.  **Connection Management**: Increased `MAX_CACHED_CONNECTIONS` to 20 and improved LRU eviction logging.
4.  **Graceful Shutdown**: Added `tenantConnector.closeAll()` to `server.js` to clean up connections on process exit.

## Test Evidence
Verification evidence remains in legacy notes and referenced backend test suites.

## Residual Risk
Residual risk is primarily external dependency and environment drift; monitor via canary, health checks, and regression suite.

## Proposed Plan

### 1. Root Cause Analysis
In `backend/src/middleware/tenantHandler.js` and `backend/src/utils/TenantConnector.js` (assumed based on usage), the system retrieves a Sequelize connection for every request: `tenantConnector.getConnection(tenant)`.
- **Vulnerability**: If `tenantConnector` simply creates a `new Sequelize()` instance every time and doesn't cache/pool them efficiently, or if the cache runs indefinitely, the application will leak file handles (if SQLite) or database connections (MySQL/PG) until the process crashes.
- **Current Scan**: The `tenantHandler` logs "Resolving tenant..." and then immediately asks for a connection.

### 2. Proposed Changes
Implement a **Connection Manager with LRU Cache**.

#### A. Modify `backend/src/utils/TenantConnector.js`
We need to ensure that we don't open 1000 connections for 1000 requests. We will use a Map or LRU cache to store active `Sequelize` instances, keyed by `tenantId`.

```javascript
const connectionCache = new Map(); // Simple cache
const MAX_CONNECTIONS = 50; // Safety limit

const getConnection = async (tenant) => {
    // 1. Check Cache
    if (connectionCache.has(tenant.id)) {
        return connectionCache.get(tenant.id);
    }

    // 2. Eviction Policy (Simple LRU logic needed here in real impl)
    if (connectionCache.size >= MAX_CONNECTIONS) {
        // Find oldest/least used and close it
        const [oldestId, oldestConn] = connectionCache.entries().next().value;
        await oldestConn.close();
        connectionCache.delete(oldestId);
    }

    // 3. Create New Connection
    const sequelize = new Sequelize(tenant.db_name, ...);
    
    // 4. Cache it
    connectionCache.set(tenant.id, sequelize);
    
    return sequelize;
};
```

#### B. Graceful Shutdown
Ensure that on process exit (SIGTERM), we iterate through `connectionCache` and call `.close()` on all instances to prevent zombie connections on the DB server.

### 3. Verification Plan

#### Automated Test (Stress Test)
1.  Simulate 100 requests to 100 *different* (or same) tenants if possible, or just spam requests.
2.  Monitor process memory usage.
3.  **Expect**: Memory usage should plateau. Without the fix, it would spike linearly.

#### Manual Verification
1.  Check database process (e.g., MySQL Workbench) "Client Connections".
2.  Run the app and click around.
3.  **Expect**: Connection count remains stable (1 per active tenant), not 1 per click.

### 4. Risk Assessment
- **Impact**: High. This prevents server crashes under load.
- **Mitigation**: Configuring the `MAX_CONNECTIONS` properly is key. Too low = performance thrashing. Too high = memory crash.
