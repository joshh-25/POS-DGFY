# Audit Finding 2.4  Premium Auto-Provisioning Lacks Rate Limiting

## Status
Resolved

## Severity
Medium

## Root Cause
The `registerCompanyRequest` endpoint auto-provisions a tenant/database if `plan === 'premium'` and PayPal verification succeeds, but lacked specific rate limiting, creating a DoS risk.

## Fix Implemented
### `backend/src/middleware/rateLimiter.js`
Added `tenantRegistrationLimiter` as a named export, following the same pattern as the existing `authLimiter` and `lookupLimiter`:
- **Window**: 1 hour
- **Max**: 5 requests/IP/hour in production, 50 in development
- **Test env**: Skipped (no impact on existing test suite)
- **Logging**: Winston warning on violation

### `backend/src/routes/adminTenants.js`
Applied the limiter as middleware on the public route:
```javascript
import { tenantRegistrationLimiter } from '../middleware/rateLimiter.js';

router.post('/register', tenantRegistrationLimiter, registerCompanyRequest);
```

## Test Evidence
Verification evidence remains in legacy notes and referenced backend test suites.

## Residual Risk
- **No breaking changes**: Admin-authenticated routes (`/approve`, `/provision`, `/delete`) are unaffected.
- **No test impact**: The `skip` function bypasses the limiter in `test` environment.
- **Legitimate users**: 5 registrations/hour is more than sufficient; the form is a one-time company setup action.
- **Premium failure edge case**: If auto-provisioning fails mid-way (zombie Tenant record), the admin can delete the record via TenantManager and the user can re-register. Recovery paths go through authenticated admin routes, which are not rate-limited.

## Finding Description
The `registerCompanyRequest` endpoint auto-provisions a tenant/database if `plan === 'premium'` and PayPal verification succeeds, but lacked specific rate limiting, creating a DoS risk.

## Severity
 Medium

## Root Cause
In `backend/src/routes/adminTenants.js`, the public `/register` route had no dedicated rate limiter:
```javascript
router.post('/register', registerCompanyRequest);
```
This endpoint triggers heavy operations on every call  bcrypt password hashing, DB uniqueness checks, and for Premium: PayPal API verification + full database provisioning (DB creation + seeding). Only the global `generalLimiter` (100 req/15 min) was applied, which is far too permissive to prevent abuse.

## Fix Applied

### `backend/src/middleware/rateLimiter.js`
Added `tenantRegistrationLimiter` as a named export, following the same pattern as the existing `authLimiter` and `lookupLimiter`:
- **Window**: 1 hour
- **Max**: 5 requests/IP/hour in production, 50 in development
- **Test env**: Skipped (no impact on existing test suite)
- **Logging**: Winston warning on violation

### `backend/src/routes/adminTenants.js`
Applied the limiter as middleware on the public route:
```javascript
import { tenantRegistrationLimiter } from '../middleware/rateLimiter.js';

router.post('/register', tenantRegistrationLimiter, registerCompanyRequest);
```

## Design Decision
The audit plan proposed creating a new `rateLimiters.js` file. The fix instead extends the existing `rateLimiter.js`  keeping all rate limiter definitions in one file, consistent with the project's existing pattern.

## Risk Assessment
- **No breaking changes**: Admin-authenticated routes (`/approve`, `/provision`, `/delete`) are unaffected.
- **No test impact**: The `skip` function bypasses the limiter in `test` environment.
- **Legitimate users**: 5 registrations/hour is more than sufficient; the form is a one-time company setup action.
- **Premium failure edge case**: If auto-provisioning fails mid-way (zombie Tenant record), the admin can delete the record via TenantManager and the user can re-register. Recovery paths go through authenticated admin routes, which are not rate-limited.
