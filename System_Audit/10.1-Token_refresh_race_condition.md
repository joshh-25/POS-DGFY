# ✅ RESOLVED - 10.1 Race Condition in Token Refresh Logic

## User Feedback
> Create a plan that could make simultaneous refresh tokens succeed

## Finding Description
The Axios interceptor lacked request queuing. Multiple concurrent 401s triggered multiple parallel refresh requests, causing race conditions with Refresh Token Rotation (RTR). Phase 47 fixed the single-tab race condition. Phase 49 extended the fix to cover multi-tab scenarios.

## Severity
🟠 High

---

## Resolution Summary

### Phase 47 (Single-Tab Fix) — 2026-02-23

**Root cause:** The response interceptor in `frontend/src/services/api.js` had no mutex. All concurrent 401s immediately fired their own `/auth/refresh-token` call, causing RTR to blacklist the first token before subsequent calls could use it.

**Fix applied:**
1. `isRefreshing` / `failedQueue` mutex — only one refresh call fires; all other 401s are queued and drained when the single refresh resolves.
2. `_retry` flag — prevents queued retries from re-entering the 401 handler and starting a second refresh cycle.
3. Queue cap (20) — requests beyond 20 are rejected immediately during a long refresh to prevent unbounded memory growth.
4. `timeout: 15000` on the refresh call — guarantees `isRefreshing` resets via `.finally()` within 15 seconds even if the server never responds.

**Key architectural finding:** The backend does not enforce single-winner RTR under simultaneous HTTP concurrency without a distributed lock (Redlock). All concurrent requests pass the blacklist check before any write completes (async Node.js event loop race). **The frontend mutex is therefore load-bearing security**, not just an optimisation.

---

### Phase 49 (Multi-Tab Fix) — 2026-02-23

**Root cause:** The `isRefreshing` mutex is a JavaScript module-level variable scoped to a single browser tab's JS heap. Each tab has its own copy. Two tabs hitting 401 simultaneously both see `isRefreshing = false` and both fire `/auth/refresh-token`. Tab A's refresh succeeds, RTR blacklists the old refresh token. Tab B fires ~50ms later with the now-blacklisted token → 401 → forced logout of a valid session.

**Fix applied: `BroadcastChannel('sku_auth')`** — a browser-native API for direct tab-to-tab messaging on the same origin. No server roundtrip. No WebSocket. No polyfill needed.

**Cross-tab messaging protocol:**
| Message Type | Sent by | Effect on Receiving Tabs |
|---|---|---|
| `token-refresh-started` | Leader tab | Follower sets `isRefreshing = true` → queues locally |
| `token-refresh-success` | Leader tab | Follower adopts new token, drains local queue, retries |
| `session-expired` | Leader tab (refresh failed) | Follower shows "Session Expired" banner |
| `auth:logout` | Any tab (deliberate logout) | Other tabs show "Session Expired" banner |

**`iAmRefreshLeader` flag:** The `.finally()` block only resets `isRefreshing` when `iAmRefreshLeader === true`. Follower tabs reset via the `onmessage` handler — they never ran `axios.post`, so no `.finally()`.

**UX decision:** The originating tab hard-redirects to `/login`; other open tabs show a non-disruptive "Session Expired" overlay banner, allowing users to finish reading before navigating to login.
