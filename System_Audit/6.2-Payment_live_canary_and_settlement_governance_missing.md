# [PARTIAL] 6.2 Payment Live Canary and Settlement Governance Missing

Severity: High
Audit area: Payments, billing operations, release evidence

## Re-Baseline Update (2026-08-05)

**Partially fixed.** `docs/ops/PAYMONGO_PRODUCTION_ACTIVATION.md` (new since this finding, last reviewed 2026-07-31) now defines the canary scenario itself (§4 "Activation proof": QR total match, one signed webhook 2xx, settlement `on_hold` → eligible, refund idempotency, platform-fee reversal in the ledger) plus a fail-safe/rollback path (§5) — satisfying remediation items 1 and 4. `productionEnvValidation.cjs:215-302` gates `COMMERCE_PAYMENTS_ENABLED`/`COMMERCE_QRPH_ENABLED`/`COMMERCE_PAYMONGO_SPLIT_ENABLED` and enforces distinct maker-checker finance identities. Still missing: no captured canary run, no provider payout/fee reconciliation artifact, and no chargeback/dispute handling exist anywhere in `docs/` — remediation items 2-3 and the corresponding acceptance gates remain unmet. **Also flagging a contradiction to resolve:** this finding's remediation item 5 says production should keep `COMMERCE_PAYMENTS_ENABLED=false`/`COMMERCE_QRPH_ENABLED=false` until live evidence exists, but `PAYMONGO_PRODUCTION_ACTIVATION.md`'s production env block sets `PAYMONGO_MODE=live` and `TENANT_REVENUE_SHARING_ENABLED=true` without mentioning either flag — the finding and the runbook currently disagree about what production is supposed to be running.

## Finding

The audit found payment safety checks and provider code, but did not find current live canary and settlement reconciliation evidence for payment provider readiness.

## Evidence

- PayMongo webhook fail-open risk is separately documented in finding 1.4 and is locally remediated.
- PayMongo QR Ph Storefront commerce-payment code is now locally integrated under ADR 0027 with migrations, landlord payment-session/refund/readiness models, `/api/v1/commerce-payments` routes, Storefront QR Ph session creation, and Admin > Payments operations.
- Local commerce-payment tests and gates pass for verifier, refund, readiness, settlement, validators, migration contract, frontend Storefront integration, dependency audits, architecture, compliance, and the local release gate.
- PayPal webhook verification fails closed in production when `PAYPAL_WEBHOOK_ID` is missing, while development and test modes can bypass.
- Current audit evidence still does not include provider-connected live canary, production webhook delivery, child-merchant webhook registration, PayMongo payout/fee reconciliation, chargeback/dispute handling, or production settlement artifacts.

## Why This Matters

Payment integration readiness requires more than local unit behavior. Live or provider-connected sandbox canary evidence should prove provider callback verification, idempotency, state transitions, settlement reconciliation, refund handling, and failure handling with real PayMongo/PayPal dashboard configuration.

## Required Remediation

1. Define payment provider canary scenarios for PayMongo and PayPal.
2. Capture webhook verification, replay rejection, refund, failed payment, chargeback/dispute, child-merchant, payout, and settlement reconciliation evidence.
3. Store canary artifacts with release evidence.
4. Add explicit production enablement gates for each provider.
5. For PayMongo commerce payments, keep `COMMERCE_PAYMENTS_ENABLED=false` / `COMMERCE_QRPH_ENABLED=false` in production until the live route returns signed-provider evidence, not merely local unit proof.

## Acceptance Gates

- Payment provider canary run is current for the target release.
- Webhook replay and invalid signature tests pass.
- Settlement reconciliation is documented with provider payout/fee evidence, not only local estimated split math.
- Production payment enablement requires current evidence.
