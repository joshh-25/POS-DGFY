# Implementation Plan - 6.4 Missing Transactional Integrity in Supplier Import

## User Feedback
> Create a plan that wraps transactions on the supplier import to make it easier for the users to import

## Finding Description
The Supplier import processes rows sequentially without a wrapping transaction.

## Severity
🟡 Medium

## Proposed Plan

### 1. Root Cause Analysis
In `backend/src/services/supplierCSVService.js`:
- The `confirmImport` function (Lines 167-225) iterates through rows and executes `Supplier.create` or `Supplier.update`.
- **Issue 1 (No Transaction)**: The operations are not wrapped in a transaction. If the server crashes mid-loop, half the data is imported.
- **Issue 2 (TOCTOU)**: It relies on `row.action` ('CREATE' or 'UPDATE') which was determined during the `previewImport` phase.
    - If "Supplier A" was created by another user *after* Preview but *before* Confirm, `confirmImport` will try to Create it again.
    - Result: Database Error (if Unique Constraint) or Duplicate Records (if no constraint).
- **Issue 3 (Race Condition)**: Checks are stale.

### 2. Proposed Changes
Refactor `confirmImport` to use a Transaction and safe Upsert logic.

#### A. Modify `confirmImport` in `supplierCSVService.js`
1.  Start a Transaction.
2.  Iterate rows.
3.  Instead of blindly trusting `action`, use `findOrCreate` or implicit checking within the transaction (pessimistic locking if needed, but for bulk import, just standard atomic checks are better).
4.  Since we want to respect the user's intent (Create vs Update), we should try to honor it but handle conflicts.
    - *Better Approach*: Just use `bulkCreate` with `updateOnDuplicate` (MySQL `ON DUPLICATE KEY UPDATE`). This is Atomic and High Performance.
    - However, since we support separate Create/Update actions, `bulkCreate` is best for "Create or Update if exists".

**Refactored Logic:**
```javascript
/* supplierCSVService.js */
export const confirmImport = async (rows, userId) => {
    const sequelize = dbStore.get('sequelize');
    const Supplier = dbStore.get('Supplier');
    
    // Start Transaction
    return await sequelize.transaction(async (t) => {
        const results = { created: [], updated: [], failed: [] };
        
        for (const row of rows) {
            if (!row.valid) { /* ... handle failed ... */ continue; }
            
            try {
                // RE-CHECK existence to fix TOCTOU
                // We lock the row if we are updating, or check existence if creating
                const existing = await Supplier.findOne({ 
                    where: { name: row.data.name }, // Assuming Name is unique key
                    transaction: t
                });

                if (existing) {
                    // It exists. Perform UPDATE, even if action was CREATE (handling the race condition gracefully)
                    await existing.update(row.data, { transaction: t });
                    results.updated.push({ ... });
                } else {
                    // It doesn't exist. Perform CREATE
                    const newSupplier = await Supplier.create({ ...row.data, status: row.data.status || 'active' }, { transaction: t });
                    results.created.push({ ... });
                }
            } catch (err) {
                 // capture error
            }
        }
        
        // If we want "All or Nothing", we throw here if results.failed.length > 0
        // But usually imports are partial-tolerant. 
        // PROPOSAL: Keep partial-success but ensure ATOMICITY Per Row (which we have) + TOCTOU Fix.
        // Actually, for "Transaction" audit item, "All or Nothing" is essentially implied unless specified otherwise.
        // Let's stick to the TOCTOU fix + Wrapping in one Transaction so if the server dies, we don't have partial commits.
        
        return { ...results };
    });
};
```

### 3. Verification Plan

#### Automated Test
1.  **Race Condition Check**:
    - Preview Import (Supplier X -> Action: CREATE).
    - Manually Create Supplier X in DB.
    - Confirm Import.
    - **Expect**: Import gracefully updates Supplier X (or fails gracefully), instead of throwing Unique Constraint error (or creating dupe).

### 4. Risk Assessment
- **Impact**: Medium (Data Consistency).
- **Performance**: Wrapping in one transaction holds the connection longer, but prevents partial-state confusion.
- **Note**: `name` might not be unique in DB schema (need to check), if not, duplicates are definitely created without this fix.
