# [OPEN] 7.2 Release Evidence Depends on Stale or Bypassable QA Paths

Severity: High
Audit area: Release governance, deployment evidence

## Finding

Prior release documentation records an emergency no-staging bypass for stale QA deployed-head evidence. The current audit did not find replacement proof that the stale-QA evidence path has been fully retired.

## Evidence

- `docs/testing/pos-readiness-status.md` documents that a production deploy used an auditable no-staging emergency bypass for stale QA deployed-head evidence.
- The same document states that a 9.2+ readiness rating is blocked until authenticated cashier/admin UAT and the next no-staging release avoids stale-QA bypass.
- Current local gates still failed, so the audit cannot treat release evidence as closed.

## Why This Matters

Release evidence must be current, reproducible, and tied to the deployed SHA. Bypassable or stale QA paths weaken confidence that production state matches audited code.

## Required Remediation

1. Replace stale QA deployed-head evidence with deterministic current SHA verification.
2. Require authenticated cashier/admin UAT for the relevant readiness claim.
3. Make no-staging bypasses time-bound, audited, and non-default.
4. Ensure production verification compares remote `HEAD`, deployed state, health, assets, and feature smoke for the exact target SHA.

## Source-Current Implementation Note

The report-mode observability release gate now reviews QA deploy-head evidence and records whether a stale-QA mismatch is matched by explicit emergency bypass metadata. This finding remains open until a production release passes without stale-QA bypass and includes deterministic deployed-SHA parity evidence.

## Acceptance Gates

- Current release evidence contains exact target SHA and deployed SHA parity.
- No stale-QA bypass is needed for the release.
- Authenticated role-based UAT evidence exists where readiness claims require it.
- Local release gate passes before production deploy.
