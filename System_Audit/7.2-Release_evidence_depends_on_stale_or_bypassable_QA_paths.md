# [OPEN] 7.2 Release Evidence Depends on Stale or Bypassable QA Paths

Severity: High
Audit area: Release governance, deployment evidence

## Finding

Prior release documentation recorded an emergency no-staging bypass for stale QA deployed-head evidence. The June 18, 2026 release evidence included a clean no-staging verdict for target SHA `4cf4c372c9eae91c6ead5932e19476f4c1b98e83`, but later June 22 Storefront map restore deployments again required owner-authorized emergency bypass because QA deploy-summary SHA evidence was stale. The current source tree now adds guarded QA promotion before the production gate and refuses production-as-QA mutation, but the finding remains open until a routine release proves exact QA deployed-head parity without emergency bypass.

- Source-current `scripts/deploy-qa-target.ps1` refuses automatic QA promotion when the configured QA SSH host/app directory match the production host/app directory.

## Why This Matters

Release evidence must be current, reproducible, and tied to the deployed SHA. Runtime proof for `eed354686109418e8766be97e05bbc90aa8ef55b` matches production, but routine release confidence still depends on proving QA parity before production instead of relying on emergency bypass.

## Required Remediation

1. Run the next routine production deploy through guarded QA promotion without emergency bypass.
2. Configure a distinct QA SSH host/app directory, or explicitly set `DEPLOY_PROMOTE_QA_BEFORE_PROD=off` when operating in production-as-QA evidence mode.
3. Keep no-staging bypasses time-bound, audited, and incident-only.
4. Ensure production verification compares deploy summary, deployed state, health runtime SHA, assets, and feature smoke for the exact target SHA.
