## Finding Description
User management routes use legacy `authorize('admin')` role checks while other modules (AI, items, etc.) use the newer `checkPermission()` system.

## Severity
🟡 Medium

## Proposed Plan

### 1. Root Cause Analysis
The codebase exhibits a "Mixed Authorization Paradigm":
- **Pattern A (Role-Based)**: `authorize('admin')` is used in some routes (`users.js`). This is coarse-grained and inflexible.
- **Pattern B (Permission-Based)**: `checkPermission('items:create')` is used in others (`items.js`). This is fine-grained and scalable.
- **The Problem**: Mixing these makes it difficult to reason about access control. A 'Manager' might technically have the 'items:create' permission in the config, but if the route is hardcoded to `authorize('admin')`, the permission is ignored.

### 2. Proposed Changes
We will standardize on **Permission-Based Access Control (PBAC)** as the single source of truth.

#### A. Audit and Update `backend/src/config/permissions.js`
Ensure that the `DEFAULT_ROLE_PERMISSIONS` map is comprehensive. Every action a role *should* be able to do must be explicitly listed.

#### B. Refactor Routes to use `checkPermission`
Iterate through route files (`users.js`, `items.js`, etc.) and replace `authorize('admin', 'manager')` with specific `checkPermission(...)` calls.

**Example Refactor in `backend/src/routes/users.js`**:
```javascript
// BEFORE (Role-Based)
router.get('/', authenticate, authorize('admin', 'manager'), userController.getAllUsers);

// AFTER (Permission-Based)
// We need to ensure 'users:view' exists in PERMISSIONS
router.get('/', authenticate, checkPermission(PERMISSIONS.SYSTEM.actions.MANAGE_USERS), userController.getAllUsers);
```

#### C. Deprecate `authorize` Middleware
Once all routes are migrated, we can mark `authorize` as deprecated or modify it to simply check for the 'admin' permission tag if needed for legacy support, but ideally, we remove it to enforce consistency.

### 3. Verification Plan

#### Automated Test
1.  Create a test user with role 'manager'.
2.  Ensure 'manager' has `users:view` permission but NOT `users:delete`.
3.  Attempt to access `GET /users` -> **Expect**: 200 OK.
4.  Attempt to access `DELETE /users/:id` -> **Expect**: 403 Forbidden.

#### Manual Verification
1.  Log in as a Manager.
2.  Try to access a route previously restricted to 'Admin' but now allowed via permission (e.g., viewing audit logs if applicable).
3.  **Expect**: Access denied or allowed based STRICTLY on the permissions array in `req.user.permissions`, not the string "role".

### 4. Risk Assessment
- **Impact**: Medium. Refactoring authorization logic always carries a risk of accidentally locking out users or opening up access.
- **Mitigation**: We will map the *exact* current effective permissions for each role before switching, ensuring 1:1 parity during the transition.
