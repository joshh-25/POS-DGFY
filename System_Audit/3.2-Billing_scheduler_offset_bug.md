## Proposed Plan

### 1. Root Cause Analysis
In `backend/src/schedulers/billingScheduler.js` (line 40):
```javascript
const targetDate = new Date(now.getTime() + range.days * 24 * 60 * 60 * 1000);
```
- **Issue**: This code assumes every day is exactly 86,400,000 milliseconds long.
- **Bug**: Across Daylight Saving Time (DST) boundaries, a day can be 23 hours (spring forward) or 25 hours (fall back). This implementation will drift by 1 hour every DST change. If the scheduler runs at midnight, it might drift into 11 PM of the *previous* day or 1 AM of the *next* day, missing the target window entirely or double-processing.
- **Impact**: Tenants might not receive expiry warnings, or "next billing date" calculations will drift away from the original signed-up calendar day.

### 2. Proposed Changes
Use native Date setters which respect local timezone/DST logic, or a robust library like `date-fns`.

#### A. Modify `checkExpiringSubscriptions`
Replace arithmetic with calendar-aware mutation.

```javascript
/* WRONG */
// const targetDate = new Date(now.getTime() + range.days * 24 * 60 * 60 * 1000);

/* CORRECT */
const targetDate = new Date(now);
targetDate.setDate(now.getDate() + range.days);
targetDate.setHours(0, 0, 0, 0); // Normalize to midnight
```
This ensures if today is March 10th and we add 7 days, we get March 17th, regardless of whether a DST shift occurred in between.
