# ✅ RESOLVED — Audit Finding 5.3: Void Logic Silently Ignores Missing Batches

## User Feedback
> Plan out to remove the discrepancy of sums of batches and global stock. They should always have integrity and correct logic calculation.

## Finding Description
When reversing a movement, if a referenced batch had already been consumed by downstream operations (Sales, Production), the system would silently allow the void — marking the batch as fully consumed and reducing global stock — causing permanent inventory discrepancies.

## Severity
🟡 Medium — Data Integrity

---

## Resolution Summary

### Root Cause
In `stockMovementService.js`, the `voidMovement` function fetched the associated FIFOBatch only at the point of update, **not** at the point of validation, and it was fetched **without** a `SELECT FOR UPDATE` lock. Two problems arose:

1. **No downstream-use guard**: If the batch had `quantity_consumed > 0` (i.e., its stock was already used in a Job Order or other consumption), the void was still allowed, creating phantom stock.
2. **Race condition**: Two concurrent void requests could both pass the `is_voided` check before either committed, resulting in a double-void.

### Fix Applied

**File**: `backend/src/services/stockMovementService.js`

1. Added `FIFOBatch` to the `include` array of the initial `findByPk` call (where `Item` and `BatchTransaction` are already eager-loaded), so the batch state is available at validation time.
2. Added `lock: transaction.LOCK.UPDATE` to the `findByPk` call — a `SELECT FOR UPDATE` database-level lock that serializes concurrent requests.
3. Added a guard that throws a 409 error if `batch.quantity_consumed > 0`:

```javascript
const originalMovement = await StockMovement.findByPk(movementId, {
    include: [
        { model: Item, as: 'item' },
        { model: BatchTransaction, as: 'batchTransactions' },
        { model: FIFOBatch, as: 'batch' }   // ← added
    ],
    lock: transaction.LOCK.UPDATE,           // ← SELECT FOR UPDATE
    transaction
});

// Guard: reject if batch has been partially or fully consumed by downstream operations
if (batch && parseFloat(batch.quantity_consumed) > 0) {
    throw new AppError(
        `Cannot void this movement: The associated batch has already been used downstream ` +
        `(consumed: ${batch.quantity_consumed}). Please revert downstream usage first.`,
        409
    );
}
```

### Error Reordering
The `is_voided` check was moved **before** the batch-consumed check so that a double-void attempt returns 400 (idempotent error) rather than confusingly hitting the 409 batch guard.
