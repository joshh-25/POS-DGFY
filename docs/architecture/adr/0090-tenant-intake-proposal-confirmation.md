# ADR 0090: Tenant Intake Proposals and Human Confirmation

## Context

Issue #2372 introduces loosely structured onboarding input for OFFICIAL and DEMO tenants. The
approved handoff selects both dgfy-admin uploads with server-side OpenAI extraction and a later
local MCP proposer. Existing tenant/account provisioning owns account creation, tenant schema
bootstrap, admin-user creation and membership. A proposal must not duplicate those operations.

## Decision

1. `[default]` Both intake surfaces converge on a landlord proposal store and the exact shared
   deterministic field validators used by admin-assisted provisioning. OpenAI handles admin uploads
   with no tools and strict structured output; the MCP caller supplies structured fields. Untrusted
   model output cannot choose role, verification, owner identity or credentials.
2. `[default]` A separate authenticated HTTP confirmation requires explicit human confirmation and
   the reviewed canonical payload/target hash. Pending proposals expire after one hour. Row locking
   serializes edits, rejection and the single-use execution claim. Claim plus approval audit commit
   before existing provisioning runs outside that transaction. Terminal failures never auto-replay;
   crashes and lost passwords require the existing operational/account recovery flows.
3. `[default]` The planned dgfy-admin UI owns review and approval. The planned MCP app exposes
   propose/get/list/update only. This is a tool-surface restriction, not cryptographic separation:
   an admin token can invoke confirmation directly over HTTP. Audit records the authenticated
   approver and `approved_via: admin_http`; it does not certify that a person clicked a UI.
4. `[default]` DEMO persists `tenants.is_demo` and requires the #653 non-production guard at proposal,
   confirmation and existing provisioning entry points. A missing NODE_ENV fails closed. OFFICIAL
   remains environment-independent. Proposal data is landlord-only and excluded from tenant cloning.
5. `[default]` Passwords are generated by existing provisioning and returned once on successful
   confirmation only. They never enter a proposal or extraction prompt/response. Recognized
   credential-bearing input is rejected; operators must exclude unlabelled secrets, which cannot be
   detected reliably. Uploaded documents remain in memory; provenance uses digest/MIME/neutral
   filename/model only. OpenAI receives minimal business/contact text, no provider tools or retained
   completion (`store:false`); provider retention policy is not represented as zero retention.
6. `[default]` ADR 0047 session, CSRF and combined tenant/account authority apply to every intake
   route. Proposal events use its Platform Admin audit log because tenant audit rows require an
   existing tenant. Existing provisioning retains the tenant/account audit. Usage logs contain
   only model/token/cost metadata. Extracted contact values remain operator-supplied, not ownership
   verification; existing admin-provisioned email semantics remain unchanged.

## Consequences and hardening

- Replay, concurrent claims, expired or stale hashes, direct unauthorized calls, and no-tenant-on-
  propose/extract must be proven in tests. Test real MySQL durability and the real existing schema
  provisioning path for both targets; do not equate mocks with tenant-schema proof.
- Existing DGFY profile/password/reset/logout/membership flows remain the account lifecycle authority.
  Independent contact verification and demo-login onboarding changes under #653 remain deferred.
- Provisioning timeout is not proof of failure. Poll the proposal; `executing` remains consumed until
  operator reconciliation. No automatic claim reclamation or retry may create a second tenant.
- Landlord migration precedes API rollout. Schema rollback retains audit/proposal/demo data and
  requires explicit operator review. No new architecture allowlist is introduced.
- Backend Phase 485 implements the HTTP/store/guard foundation; UI review and MCP tool-list proof
  remain later PRs. No end-to-end UI or MCP acceptance is claimed by this backend change.

## Validation

- Tenant intake use-case/extraction tests, existing admin-provisioning tests and Platform Admin
  route-classification tests; real MySQL proof through `scripts/verify-tenant-intake.mjs`.
- `npm run check:architecture`, `npm run check:adr`, `npm run lint:docs`, compliance declaration
  validation, tenant-schema coverage and develop-base app-version checks.
- Post-merge operational review covers provider configuration/PII, landlord-first rollout, real
  admin-session transport, UI consent and MCP omission of confirmation.
