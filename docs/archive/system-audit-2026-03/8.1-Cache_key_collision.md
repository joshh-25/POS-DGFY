## Finding Description
The `cacheService` provides raw access to Redis without automatically namespacing keys by `tenantId`.

## Severity
 Medium

## Proposed Plan

### 1. Root Cause Analysis
In `backend/src/services/cacheService.js`:
- The service exports `get(key)` and `set(key)` which pass the string directly to Redis.
- **Vulnerability**: There is no enforcement of Tenant ID namespacing.
- **Scenario**:
    - Developer A writes a new feature: "Cache user profile by ID".
    - `cacheService.set('user_123', profileData)`.
    - Tenant A has User 123. Tenant B has User 123.
    - Tenant B logs in, hits the cache, and sees Tenant A's profile data.
- **Current Status**: Only `authService` uses it (`blacklist:token:...`), which is safe by coincidence (tokens are globally unique).
- **Risk**: High latency bomb (future collision) waiting to happen.

### 2. Proposed Changes
Enforce Tenant Namespacing in `cacheService`.

#### A. Modify `cacheService.js`
1.  Integrate `dbStore` (which holds `tenantId` in ALS).
2.  Prefix all keys with `tenant:{id}:` unless explicitly opted out (e.g. for global tokens).

```javascript
/* cacheService.js */
import dbStore from '../utils/dbStore.js';

const getScopedKey = (key) => {
    // If key explicitly requests global scope (e.g. 'global:xxx'), allow it.
    if (key.startsWith('global:') || key.startsWith('blacklist:')) return key;

    const store = dbStore.getStore();
    const tenantId = store?.tenantId;
    
    if (tenantId) {
        return `tenant:${tenantId}:${key}`;
    }
    // Fallback? Or Warn?
    return key; 
};

export const set = async (key, value, ttl) => {
    const scopedKey = getScopedKey(key);
    // ... proceed ...
};
```

## Final Review & Fixes Applied

 **Core Fix Verified**: The primary fix for this issue was already implemented. `getScopedKey()` ensures all cache writes are scoped by `tenantId` natively, and defaults to a `system:` prefix if there is no tenant context.

A deep analysis identified **two remaining gaps** which have now been patched:
1. **Unscoped `clear()` method**: The `cacheService.clear()` method previously passed raw patterns to Redis, which could have allowed a tenant to delete keys matching `user:*` across the entire system. This was patched by applying `getScopedKey()` to the `clear()` wildcard pattern.
2. **Silent fallbacks**: If `cacheService` was used outside a tenant context (e.g. from a background job or during early development routes), it silently defaulted to the `system:` namespace. A debug log has been added when it falls back to `system:` to help developers catch accidental unscoped usage.

**Note on Blacklist Keys**: The original audit proposed exempting `blacklist:` keys from scoping. This was **not** implemented, but upon review, the current behavior (scoping blacklist keys) is more robust. Since both `authService.blacklistToken()` (write) and `authService.isTokenBlacklisted()` (read) run *inside* the `tenantHandler` middleware, their scopes correctly match, preventing any cross-tenant token invalidation conflicts.
