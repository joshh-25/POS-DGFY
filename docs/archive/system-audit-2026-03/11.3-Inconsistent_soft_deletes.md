## Finding Description
Soft delete behavior is inconsistent across entities and query paths. The issue is no longer "missing paranoid for Item" only. The real issue is mixed patterns and incomplete deleted-record guards.

## Final Policy Decision
1. Standardize on **manual-only soft delete** for `Item`, `Supplier`, and `User`.
2. Default API behavior for soft-deleted records is **`404 Not Found`**.
3. `410 Gone` is reserved for future privileged admin/audit endpoints only.

## Root Cause
1. The codebase evolved with two patterns in parallel (manual + paranoid).
2. No centralized active-record query contract was enforced for soft-deletable entities.
3. Audit note remained stale after partial fixes.

## Execution Plan (Completed)

### Phase 1: Define and enforce soft-delete contract
1. Add canonical helper/scopes for soft-deletable entities:
   - `activeWhere` helper: `{ deleted_at: null }`
   - entity-specific active guards:
     - Item: `deleted_at: null` + `status != 'inactive'`
     - Supplier: `deleted_at: null` + `status != 'inactive'`
     - User: `deleted_at: null` + `is_active` rules per endpoint
2. Remove hybrid ambiguity:
   - Keep behavior manual-only across services.
   - Stop relying on Sequelize paranoid semantics as authoritative business behavior.

### Phase 2: Patch all read/update/delete paths
1. Supplier service hardening:
   - `getSupplierById`, `updateSupplier`, `finalizeSupplier`, `deleteSupplier`, and item-assignment paths must return 404 when `deleted_at != null`.
2. User service hardening:
   - Add `deleted_at: null` filter to export/list/helper endpoints where deleted users must not appear.
   - Block role/status/permission changes on soft-deleted users (404).
3. Item service consistency:
   - Ensure all relevant fetch/update paths apply the same manual active contract and return 404 for deleted records.
4. Middleware/auth consistency:
   - Keep login denial for removed users.
   - Ensure token refresh/auth paths do not silently revive soft-deleted accounts.

### Phase 3: Error semantics standardization
1. All default endpoints return `404` for soft-deleted resources.
2. Keep error payload format consistent with existing API error standard.
3. Document the 404 policy in API and audit docs.

### Phase 4: Regression test implementation
1. Add integration tests per entity:
   - delete then fetch detail -> 404
   - delete then mutate (update/delete again) -> 404
   - list endpoints exclude deleted records
2. Add negative tests:
   - deleted users cannot be role-updated, status-toggled, or exported
   - deleted suppliers cannot be edited or linked to new supplier-item rows
3. Add contract tests for error semantics:
   - verify 404 for deleted resources in default endpoints.

### Phase 5: Documentation and rollout
1. Update:
   - `docs/guides/DELETE_ARCHIVE_GUIDE.md`
   - `docs/api/specification.md`
   - `docs/database/schema.md` (behavioral notes)
2. Add deployment validation checklist and production smoke tests.

## Critical Evaluation

### Strengths
1. Predictable behavior: all teams know exactly how delete/read/update behaves.
2. Better auditability: deleted records remain traceable with actor and timestamp.
3. Lower surprise in frontend: unified 404 behavior avoids endpoint-specific edge cases.

### Risks and Weak Points
1. Manual policy is only as strong as enforcement coverage in services.
2. Existing `findByPk` usage can reintroduce leaks if new endpoints skip helper/scope.
3. Legacy scripts/report exports may bypass API-level protections.

### Mitigations
1. Enforce helper/scope usage in service code review checklist.
2. Add focused regression tests for every soft-deletable entity.
3. Include deleted-record checks in endpoint templates and QA smoke tests.
