## Finding Description
There were originally two documented scaling vulnerabilities under this audit item:
1. `billingScheduler` used `node-cron` without a locking mechanism, running multiple times across scaled instances.
2. `tempFileService` uses a local In-Memory `Map` to store references to generated CSV files, breaking horizontal scaling.

## Severity
 Medium

## Proposed Plan

### 1. Root Cause Analysis
**A. `billingScheduler.js` (Already Fixed)**
- The scheduler runs locally on *every* instance of the backend.
- **Analysis**: This issue has **already been resolved** in the codebase using `cacheService.acquireLock` (a distributed Redis lock).

**B. `tempFileService.js` (Active Vulnerability)**
- **Vulnerability**: The service uses `const tempFiles = new Map()` to store temporary CSV data.
- **Scenario**: 
  - User requests CSV export on Instance A. Instance A saves data to its local Map and returns a download link with a UUID.
  - User's browser follows the link, but load balancer routes the download request to Instance B.
  - Instance B checks its purely local Map, finds nothing, and returns a 404 Error.
- **Analysis**: Code assumes a single-server deployment. Local memory cannot be used for multi-step state in a clustered environment.
In `backend/src/schedulers/billingScheduler.js`:
- The `initBillingScheduler` function starts a standard `node-cron` job.
- **Vulnerability**: The scheduler runs locally on *every* instance of the backend.
- **Scenario**:
    - Production environment scales to 3 instances (for high availability).
    - At midnight, all 3 instances wake up.
    - All 3 instances query the DB for expiring subscriptions.
    - All 3 instances send emails.
    - Result: Users receive 3x "Subscription Expiring" emails. If auto-charge logic existed, they would be triple-charged.
- **Analysis**: Code assumes a single-server deployment.

### 2. Proposed Changes
Migrate `tempFileService.js` to use Redis via `cacheService` instead of a local Map.

#### A. Modify `tempFileService.js`
1. Remove `const tempFiles = new Map();` and `tempFileService.js` dependency on filesystem/local variables.
2. In `storeTemporaryFile`, replace Map insert with `cacheService.set('temp_file:{id}', data, 3600)`.
3. In `getTemporaryFile`, replace Map lookup with `cacheService.get('temp_file:{id}')`.
4. Rely on Redis native TTL caching to auto-expire the temporary files, turning `cleanupExpiredFiles()` into a no-op instead of forcing a local setInterval/cron.

### 3. Verification Plan

#### Manual Verification
1.  Start 2 backend processes locally (different ports).
2.  Trigger the scheduler manually (or wait).
3.  **Expect**: Only one process logs "Sending expiry warning". The other logs "Lock held...".
