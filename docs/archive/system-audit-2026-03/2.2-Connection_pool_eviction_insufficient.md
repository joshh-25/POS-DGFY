# 2.2 Connection pool eviction is insufficient for high load

## Status
FIXED (2026-02-16)

## Severity
Critical

## Root Cause
`evictOldestConnection` only removes **one** connection when the limit is reached. If 10 concurrent requests come in for 10 different tenants, the pool will expand beyond `MAX_CACHED_CONNECTIONS` before the eviction logic can reduce the count.

## Fix Implemented
### 1. Concurrency Guard (`pendingConnections` Set)
- Added `pendingConnections` Set to track in-flight connection creations.
- When a connection is being created for a tenant, concurrent requests for the **same** tenant poll-wait (100ms intervals, 5s max) instead of creating duplicates.
- Size check now counts `connections.size + pendingConnections.size` to prevent pool overflow.
- `finally` block always removes from `pendingConnections`, even on error.

### 2. Batch Eviction (`evictConnections(count)`)
- New method sorts connections by `lastUsed` ascending and evicts `count` oldest in parallel via `Promise.allSettled()`.
- `evictOldestConnection()` retained as backward-compatible wrapper.

### 3. Periodic Idle Cleanup
- `startPeriodicCleanup()` runs every 60s, closing connections idle for >10 minutes (`IDLE_TIMEOUT_MS`).
- `stopPeriodicCleanup()` clears the interval.
- Interval uses `.unref()` to not block process exit.
- Started on server boot, stopped on graceful shutdown.

### 4. Sequelize Pool Tuning
```javascript
pool: {
    max: 5,
    min: 0,
    acquire: 30000,
    idle: 5000,  // Reduced from 10s to 5s
    evict: 1000  // NEW: Check for idle connections every 1s
}
```

### 5. Observability
- `getPoolStats()` method returns `{ total, pending, capacity, utilizationPercent }`.
- `/health` endpoint now reports `tenantPool` stats with warning at >90% utilization.
- Pool size logged on every connection creation and eviction event.

## Finding Description

## Severity
 Medium (User considers Critical)

## Root Cause
Four issues in `backend/src/utils/TenantConnector.js`:

1. **Race condition**: `getConnection()` is async  multiple concurrent calls could all pass the `connections.size >= MAX_CACHED_CONNECTIONS` check before any eviction completed, causing unbounded pool growth.
2. **Single eviction**: `evictOldestConnection()` only removed one connection per call, insufficient when many new tenants arrive simultaneously.
3. **Dead constant**: `IDLE_TIMEOUT_MS` (10 min) was defined but never used  no periodic cleanup existed.
4. **Missing Sequelize `evict` config**: The pool config lacked the `evict` parameter that controls how frequently Sequelize checks for idle internal connections.

## Fix Applied

### 1. Concurrency Guard (`pendingConnections` Set)
- Added `pendingConnections` Set to track in-flight connection creations.
- When a connection is being created for a tenant, concurrent requests for the **same** tenant poll-wait (100ms intervals, 5s max) instead of creating duplicates.

- `finally` block always removes from `pendingConnections`, even on error.

### 2. Batch Eviction (`evictConnections(count)`)

- `evictOldestConnection()` retained as backward-compatible wrapper.

### 3. Periodic Idle Cleanup
