## Critical Anti-Patterns

| Pattern | Description | Severity | Prevention Mechanism |
|---------|-------------|----------|---------------------|
| MySQL named-lock + Sequelize connection pool mismatch | GET_LOCK/RELEASE_LOCK are session-scoped; a naive `coreSequelize.query('SELECT GET_LOCK(...)')` followed later by a separate `.query('SELECT RELEASE_LOCK(...)')` can silently execute on two *different* pooled connections, making the lock a no-op with no error. | advisory | Any future concurrency-guard fix using MySQL named locks with Sequelize must pin both calls to one physical connection (Sequelize's unmanaged-transaction-as-connection-affinity-handle technique). Note: dgfy-temp EC2 (see below) now provides real MySQL, so this can finally be empirically tested if F-04 is picked up. |
| Sequelize `addIndex` `type:` vs `using:` | `type:` in Sequelize's `addIndex` options is for `UNIQUE`/`FULLTEXT`/`SPATIAL` only — passing `type: 'BTREE'` generates literally invalid SQL (`ADD BTREE INDEX ...`). BTREE is an index *algorithm*, set via `using:`, not a `type:`. | blocking | Found in `apps/dgfy-migration-runner/src/migrations/schema/20260714101000-enable-storefront-discovery-geo-search.cjs`, blocking `schema migrate` against any fresh `dgfy_core`. Fixed (`using: 'BTREE'`), but **fix is uncommitted** — commit it before building anything else on top. Was never caught by CI because its only test coverage is a `RUN_PHASE10_STOREFRONT_COMMERCE_SCHEMA_INTEGRATION`-gated test that skips without real MySQL credentials — check whether other new migrations need the same live-DDL scrutiny before trusting they'll actually apply. |
| `schema migrate` needs the empty target database pre-created | Neither `dgfy_core` nor a `dgfy_business_*` target database is auto-created by `schema migrate` — it only runs Sequelize migrations (tables) against an *already-existing* empty database. `CREATE DATABASE` must happen out-of-band first (confirmed via `docs/database/dgfy-migration-rehearsal.md`'s own "provision disposable schemas" step, which we'd initially skipped). | advisory | Any rehearsal/cutover script must `CREATE DATABASE IF NOT EXISTS` for every target (core + each business db) before calling `schema migrate --confirm-destructive`. |
| `schema migrate` transient zero-pending anomaly | One observed instance: immediately after creating 26 fresh empty business databases, `schema migrate` reported `total_pending=0 executed=0` for all business targets (silently no-op, not an error) despite `DGFY_BUSINESS_DB_NAMES` being correctly passed and parsed (verified directly via `validateEnv()`). An immediate identical retry succeeded fully (208/208 executed). Root cause not found — did not reproduce on retry. | advisory | If `schema migrate` reports 0 pending against known-fresh business databases, don't trust it — retry once and verify via `SHOW TABLES` before assuming success or failure. |
