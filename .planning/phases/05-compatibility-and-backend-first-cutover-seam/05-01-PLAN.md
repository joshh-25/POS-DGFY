<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| manifest file → CI validator | The manifest is human-authored config consumed by a CI script; its `tests` path strings are untrusted input that the validator resolves against the filesystem. |
| repo working tree → reconciliation scan | Source files carry `@compat-seam` markers the validator scans; a marker without a complete manifest entry must not silently pass. |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-05-01 | Tampering | manifest `tests` path field → fs access in check-compat-seams.js | medium | mitigate | Reject absolute paths and any path containing `..`, and reject paths resolving outside REPO_ROOT, BEFORE fs.existsSync — mirror lint-docs.js path-safety idiom (Task 2, ASVS V5). |
| T-05-02 | Tampering | manifest schema (unknown/missing fields) | low | mitigate | Strict schema validation: reject unknown top-level/per-seam keys and unknown type/status enum values; completeness gate rejects empty governance fields (Task 2). |
| T-05-03 | Elevation | reconciliation bypass (code seam with no manifest entry) | medium | mitigate | Bidirectional code↔manifest reconciliation fails the build on marker-without-entry and active-entry-without-marker (Task 2). |
| T-05-SC | Tampering | npm dependency surface | low | accept | JSON fallback adds zero packages (RESEARCH Package Legitimacy Audit); no install task in this plan, so no supply-chain checkpoint required. |
</threat_model>
