## Rationale

This plan is within the existing DGFY API boundary plus an additive migration-runner schema contract update. It does not create a separate tenancy route module and does not change public endpoint organization from D-12/D-13. The additive `staff_invitations` tenant table is required because 04-VERIFICATION identified invitation durability as missing and the current tenant schema has no durable invitation-token record.

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| client -> businesses location/staff routes | Authenticated input crosses into branch and staff use cases. |
| landlord registry -> tenant database | Business id resolves to a server-owned tenant database name. |
| invitation token -> tenant DB | Raw token from request maps to a hash-only durable invitation record. |
| API process -> tenant MySQL | TenantConnector opens per-tenant Sequelize connections. |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-04-07-01 | Tampering | LocationRepository tenant DB resolution | high | mitigate | Resolve database names only from landlord registry metadata and never from public request fields. |
| T-04-07-02 | Information Disclosure | staff invitations | high | mitigate | Persist token hashes only; raw invitation token is limited to the accepted response/email path. |
| T-04-07-03 | Repudiation | invitation acceptance | medium | mitigate | Persist status and accepted_at; tests prove replay rejection. |
| T-04-07-04 | Elevation of Privilege | staff/location writes | high | mitigate | Keep owner/manager authorization in use cases before repository writes. |
| T-04-07-05 | Denial of Service | TenantConnector connection fanout | medium | mitigate | Reuse cached connections and return stable ApplicationResult failures for unreachable tenant DBs. |
