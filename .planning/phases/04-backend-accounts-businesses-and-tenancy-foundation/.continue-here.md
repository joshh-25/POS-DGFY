## Critical Anti-Patterns

| Pattern | Description | Severity | Prevention Mechanism |
|---------|-------------|----------|---------------------|
| MySQL TRUNCATE vs FK constraint | `Model.destroy({truncate:true})` issues a raw `TRUNCATE`, which MySQL/InnoDB unconditionally refuses when ANY table has a live FK constraint referencing the target — regardless of row count. Affected 9 dgfy-api test files whose `afterEach` truncated `accounts` while `business_memberships` FK-references it. | advisory | Already fixed everywhere it was found this session (commits 34108f0e, 83b7bdf5, 1a5f4543). If a NEW test file adds a similar `afterEach` truncate pattern, don't repeat it — use per-test-unique literals + a single `afterAll` `DROP DATABASE` instead (see `tests/e2e/phase4FullFlow.test.js` for the reference pattern). |
| Jest ESM `unstable_mockModule` leaks across `describe` blocks | Registrations persist across `jest.resetModules()` within the same file — a later block's real dynamic import silently inherits an earlier block's mock for the same specifier. Bit `activateTenant.test.js` twice (two different leaked specifiers) before the real fix (move the real-import block to the very top of the file, before ANY mock of any specifier it transitively needs). | advisory | Already fixed (commit 4f932d8b). If writing a new test file with both mocked unit tests and a real DB-backed integration block in the same file, put the DB-backed block first. |

<decisions_made>

- MySQL/InnoDB unconditionally refuses `TRUNCATE` on any table referenced by a live FK constraint, regardless of row count — verified by reading Sequelize's own `bulkDelete`/`truncateTableQuery` source, not just observed behavior. This explains why 9 different dgfy-api test files' `afterEach Account.destroy({truncate:true})` were doomed from the start.
- Fix pattern for that bug: delete the `afterEach` entirely, rely on each file's already-existing per-test-unique `business_handle`/email literals plus its existing `afterAll DROP DATABASE` — matches `phase4FullFlow.test.js`'s already-proven strategy.
