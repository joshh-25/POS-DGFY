**Output:** Working account model, repository, and use cases with comprehensive unit and integration tests.

<task type="auto">
  <name>Task 3: Create Account Use Cases — accountUseCases.js</name>
  <files>backend/src/modules/accounts/usecases/accountUseCases.js</files>
  <action>
Create `backend/src/modules/accounts/usecases/accountUseCases.js` with use case builders (factory functions) that return use cases. Implement:

**buildRegisterAccountUseCase({repository, hashPassword})**
Input: `{email, password, first_name, last_name, phone}`
- Validates email (required, valid format, not duplicate)
- Validates password (required, min 8 chars)
- Hashes password using hashPassword (bcrypt)
- Calls repository.create({email, password_hash, first_name, last_name, phone, status: 'active', email_verified_at: null})
- Returns `ApplicationResult.success({account})`
- Returns `ApplicationResult.failure({code: 'DUPLICATE_EMAIL', message: '...'})` if email exists
- Returns `ApplicationResult.failure({code: 'VALIDATION_ERROR', message: '...'})` if validation fails
- Per D-01: account is immediately created but marked unverified (email_verified_at is null)

**buildLoginAccountUseCase({repository})**
Input: `{email, password}`
- Validates email, password (required)
- Looks up account by email
- If not found: returns `ApplicationResult.failure({code: 'INVALID_CREDENTIALS'})`
- Uses bcrypt.compare(password, account.password_hash)
- If mismatch: returns `ApplicationResult.failure({code: 'INVALID_CREDENTIALS'})`
- If match: updates last_login_at, generates session token (caller-supplied or using existing backend auth pattern per D-07)
- Returns `ApplicationResult.success({account, sessionToken, businesses: []})`
- businesses array will be populated in Wave 3 (stub empty array for now)

**buildUpdateAccountProfileUseCase({repository})**
Input: `{accountId, updates: {email?, password?, first_name?, last_name?, phone?}}`
- Validates accountId exists
- For each provided update: validate field constraints (email unique, password min length)
- If password included: hash it
- Calls repository.update(accountId, sanitized_updates)
- Returns `ApplicationResult.success({account})`
- Returns appropriate DomainError if validation fails

**buildGetAccountUseCase({repository})**
Input: `{accountId}`
- Looks up account by ID
- Returns `ApplicationResult.success({account})`
- Returns `ApplicationResult.failure({code: 'NOT_FOUND'})` if not found

**buildGetAccountForAuthorizationUseCase({repository})**
Input: `{accountId, requestingAccountId, role}`
- If requestingAccountId === accountId (self): return success
- If role === 'admin': return success (role comes from request context, implemented Wave 2)
- Otherwise: return failure(UNAUTHORIZED)
- Used by account lookup endpoint (Wave 2)

**Pattern Requirements:**
- Each use case is returned by a builder function (factory pattern)
- Use cases receive dependencies (repository, hashPassword) via closure
- All use cases return ApplicationResult (success/failure)
- Use DomainError for domain-level failures (not generic Error)
- No database access (all via repository)
- No HTTP concerns (no res/req)

**Reference:**
See `backend/src/modules/dgfy/usecases/dgfyAuthUseCases.js` for existing pattern examples.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| User Input → Registration | Unverified email/password from HTTP request |
| User Input → Login | Unverified email/password from HTTP request |
| Account DB ← Use Case | Only AccountRepository can read/write; use cases enforce business rules |
| Session Token → Client | JWT/opaque token returned by login; client stores and sends in future requests |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-04-01 | Tampering | Password Storage | high | mitigate | Use bcrypt (10 rounds minimum per CONVENTIONS.md); never store plaintext password; implement in use case, not model |
| T-04-02 | Information Disclosure | Email Unique Index | medium | mitigate | Email uniqueness enforced via DB constraint; account lookup by email returns only to self/admin (access control in Wave 2 controller) |
| T-04-03 | Denial of Service | Registration Rate Limiting | medium | accept | Rate limiting is a Wave 2 controller concern (not applicable to model/repository in Wave 1); defer to Phase 5 if needed |
| T-04-04 | Repudiation | Account Audit | low | accept | Audit log writing deferred to Wave 3 (business audit logs are created on business-related actions, not account creation in V1) |
| T-04-05 | Elevation of Privilege | Account Status | medium | mitigate | Account status enum limited to {active, suspended, archived}; only admin can change status (enforced in Wave 2+ controller, not in model) |
| T-04-SC | Supply Chain | npm/pip installs | high | mitigate | No new external dependencies in Wave 1 (bcryptjs, Sequelize already in package.json from Phase 3); slopcheck + blocking human checkpoint if new deps added |

</threat_model>
