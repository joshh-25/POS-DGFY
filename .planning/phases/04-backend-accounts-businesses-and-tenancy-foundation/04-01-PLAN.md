## Objective

**Wave 1: Account Foundation — Clean Architecture** establishes the account domain with separate Entities layer (business rules) and Repositories (data access adapters). Models are persistence-only; use cases operate on domain entities.

**Why this matters:** Without a solid account foundation with clear separation between persistence and domain logic (Clean Architecture), all later domain work gets tangled. Wave 1 establishes the Entities ↔ Repository ↔ Model translation pattern that all later waves follow.

**Output:** Working account Sequelize model, domain entity, repository adapter, and use cases with comprehensive tests. All follow Clean Architecture + SOLID principles.

**Repository Pattern (Repository-as-Adapter):**
```javascript
export class AccountRepository {
  constructor(accountModel) {
    this.accountModel = accountModel; // Sequelize model
  }

  // Translate Model → Entity
  async create(accountData) {
    const model = await this.accountModel.create(accountData);
    return this.modelToEntity(model);
  }

  // Query → Translate Model → Entity
  async findById(id) {
    const model = await this.accountModel.findByPk(id);
    return model ? this.modelToEntity(model) : null;
  }

  // Translate Model ↔ Entity
  modelToEntity(model) {
    return new AccountEntity({
      id: model.id,
      email: model.email,
      // ... copy all fields
    });
  }

  entityToModel(entity) {
    return {
      id: entity.id,
      email: entity.email,
      // ... copy all fields
    };
  }
}
```

**Methods to Implement:**
- `create({email, password_hash, first_name, last_name, phone})` — inserts, returns entity
- `findById(id)` — returns entity or null
- `findByEmail(email)` — case-insensitive query, returns entity or null
- `findByPhone(phone)` — returns entity or null
- `update(id, updates)` — updates fields, returns updated entity
- `modelToEntity(model)` — translation helper
- `entityToModel(entity)` — translation helper

**Key Points (Clean Architecture):**
- Repository owns ALL Sequelize queries (no queries elsewhere)
- ALL data access filtered through this file
- Translates Model ↔ Entity at boundaries
- Use cases call repository methods; receive entities back
- No business logic here; just data access + translation

**Error Handling:**
- Return null on not-found (let caller decide what to do)
- Let DB errors bubble (caller validates)
- No validation here; repository is data-access only

**Dependency Injection:**
- Repository receives Sequelize model via constructor
- Use case builds repository with injected model
- Testable: mock model for unit tests

**Use Case Builder Pattern:**
```javascript
export function buildRegisterAccountUseCase({repository, accountEntity, hashPassword}) {
  return async (input) => {
    // Validate using entity validators
    if (!accountEntity.validateEmailFormat(input.email)) {
      return ApplicationResult.failure({code: 'INVALID_EMAIL', message: '...'});
    }
    if (!accountEntity.validatePasswordStrength(input.password)) {
      return ApplicationResult.failure({code: 'WEAK_PASSWORD', message: '...'});
    }
    
    // Check for duplicate (business rule)
    const existing = await repository.findByEmail(input.email);
    if (existing) {
      return ApplicationResult.failure({code: 'DUPLICATE_EMAIL', message: '...'});
    }
    
    // Hash password
    const password_hash = await hashPassword(input.password);
    
    // Create entity (use case builds the entity)
    const accountEntity = new AccountEntity({
      email: input.email,
      password_hash,
      first_name: input.first_name,
      last_name: input.last_name,
      phone: input.phone,
      status: 'active',
      email_verified_at: null // per D-01
    });
    
    // Persist via repository
    const created = await repository.create(accountEntity);
    
    return ApplicationResult.success({account: created});
  };
}
```

**Use Cases to Implement:**
- `buildRegisterAccountUseCase({repository, accountEntity, hashPassword})` — validates, hashes, creates account (unverified per D-01)
- `buildLoginAccountUseCase({repository, bcrypt})` — validates email/password, updates last_login_at, returns session token + business list
- `buildUpdateAccountProfileUseCase({repository, accountEntity, hashPassword})` — validates, updates fields, returns updated account
- `buildGetAccountUseCase({repository})` — lookup by ID, returns entity
- `buildGetAccountForAuthorizationUseCase({repository})` — returns account if authorized (self or admin), else failure

**Key Points (Clean Architecture):**
- Use cases receive DEPENDENCIES via closure (repository, entity class, hashPassword function)
- Use cases CALL repository methods; receive entities back
- Use cases use entity validators to enforce business rules
- Use cases return ApplicationResult ALWAYS (never throw)
- Use cases orchestrate: validate input → call repository → validate result → return ApplicationResult
- Dependency Inversion (D): use cases depend on repository abstraction (injected), not concrete implementation

**No HTTP in use cases. No model queries. All data access via repository. All validation via entity or repository calls.**

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| HTTP Client → Controller | Untrusted input (email, password, personal data); controller validates via use case |
| Use Case → Repository | Trusted (internal); repository receives validated data |
| Repository → Database | Trusted (internal); SQL executed via Sequelize ORM (parameterized) |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-04-01 | Tampering | Password Hash | high | mitigate | Use bcrypt with cost factor ≥10; never store plaintext passwords; accountUseCases enforces hashing before repository.create() |
| T-04-02 | Information Disclosure | Account Lookup | high | mitigate | Per D-04, GET /accounts/:id endpoint enforces authorization (self or admin) in controller before calling use case |
| T-04-03 | Elevation of Privilege | Account Registration | medium | mitigate | New accounts created with status='active', no special privileges; per D-01, email verification is optional/configurable |
| T-04-04 | Denial of Service | Email Uniqueness | medium | mitigate | Unique constraint on email column (DB enforced); use case validates before insert; duplicate email returns 409 (user-friendly) |
