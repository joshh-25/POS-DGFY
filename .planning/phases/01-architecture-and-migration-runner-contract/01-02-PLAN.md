<objective>

</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Runner process → dgfy_migration_meta | Runner reads/writes its own permanent audit schema, independent of landlord schema state |
| Runner process → REPORT_DIR (mounted volume) | Runner writes report/summary files that must survive container exit |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-01-04 | Tampering | src/metadata/bootstrap.js (ensureMetadataSchema) | high | mitigate | On every run past the first, existing `dgfy_migration_meta` table structure is compared column-by-column against the expected contract; any mismatch throws `MetadataSchemaError` instead of running against a possibly-corrupted audit store. |
| T-01-05 | Repudiation | src/metadata/bootstrap.js (recordCommandStart/recordCommandComplete), src/reports/reportWriter.js | high | mitigate | Every command execution writes a DB-backed audit row (command/actor/runtime_mode/timestamps/exit_status) plus a durable JSON+summary report file pair under `REPORT_DIR`, so no command run can be silently unaccounted for after the one-shot container exits. |
| T-01-06 | Information Disclosure | src/reports/reportWriter.js, src/reports/summaryWriter.js | medium | accept | Reports may include DB host/target names but never raw credentials (Plan 03's command handlers only ever pass `config.targetDb.name`/`host` into report payloads, not passwords) — accepted because report contents are operator-facing artifacts scoped to `REPORT_DIR` access, not network-exposed. |

</threat_model>
