# Phase 13.5: Staff Authentication Model Correction - Context

**Gathered:** 2026-07-14
**Status:** Inserted blocker before Phase 14

<domain>
## Phase Boundary

Correct the DGFY staff authentication architecture discovered during Phase 13 rehearsal.

The current ADR 0028 and `dgfy_business_*` tenant foundation assume staff authentication is DGFY-account based: `staff_accounts` is profile/authorization only, `account_staff_assignments` links a DGFY account to staff, and invited staff are expected to be existing DGFY accounts. That is not the intended product model.

The intended model is tenant-local-staff-first:

- A business can create/invite a staff user scoped to that business.
- That staff user can authenticate without a global DGFY account.
- The staff user may optionally link to a global DGFY account later for unified identity/company switching.
- Legacy business-isolated staff users (`tenant_db.users`) already have `password_hash`, invitation state, POS PIN state, roles, and permissions; the migration must not silently discard staff login capability.

This phase is cross-boundary: architecture ADR, tenant schema, migration runner mapping/verify rules, and API staff auth/onboarding assumptions must converge before Sales History migration and cutover planning continue.
</domain>

<decisions>
## Locked Direction

- **D-13.5-01:** DGFY global accounts are optional for staff, not mandatory.
- **D-13.5-02:** Tenant-local staff credentials must exist as first-class target data, either directly on `staff_accounts` or in a same-tenant `staff_credentials` table. The exact table shape is this phase's design decision; do not continue with the current no-credential staff schema unchanged.
- **D-13.5-03:** `account_staff_assignments` remains useful, but it represents optional DGFY-account linkage to a tenant-local staff profile. It is not the only staff access path.
- **D-13.5-04:** Legacy `tenant_db.users.password_hash` must be migrated or intentionally invalidated with an explicit reset/reinvite flow. No silent discard.
- **D-13.5-05:** Pending DGFY memberships/invites are not product/inventory blockers. Accepted DGFY memberships should link when valid, but missing/pending DGFY membership does not imply a staff account cannot exist or log in tenant-locally.

## Current Conflict

ADR 0028 currently says:

- IMS user invitations are DGFY-account invitations.
- Tenant-local password setup for invited business users is retired by default.
- New invited users must be selected registered DGFY accounts.
- POS DGFY unlock and IMS switcher require accepted DGFY membership.

That conflicts with the intended product requirement. This phase must amend ADR 0028 rather than work around it in migration code.
</decisions>

<requirements>
## Requirements Mapped

- STAFF-01: Tenant-local staff authentication remains supported in the DGFY tenant schema.
- STAFF-02: Linking a tenant-local staff profile to a global DGFY account is optional.
- STAFF-03: Legacy tenant `users.password_hash`, invitation/setup state, and POS PIN implications have an explicit migration target or documented reset/reinvite flow.
- STAFF-04: ADR 0028, database docs, migration map, schema contracts, and verification gates are amended to the tenant-local-staff-first model.
</requirements>

<success_criteria>
## Success Criteria

1. ADR 0028 no longer states that new staff invitations must be DGFY-account-only or that tenant-local password setup is retired for staff.
2. The target tenant schema has a durable credential representation for staff-local login, or a documented credential reset flow with explicit operator/user action.
3. Migration maps legacy tenant users into staff profiles plus credential handling without copying secrets into reports.
4. DGFY membership/assignment migration is optional linkage evidence, not mandatory staff existence/auth evidence.
5. Verification can report staff credential/linkage status separately from product/inventory fidelity, so Phase 13 data proof is not red because a pending DGFY invite exists.
</success_criteria>

<threat_model>
## Threat Notes

- Do not infer DGFY account access from matching email/phone. Optional DGFY linking must still require explicit link proof.
- Do not expose password hashes, POS PIN hashes, raw invite tokens, reset tokens, or temporary passwords in migration reports.
- Tenant-local staff credential migration must be additive and reversible enough for rehearsal reset; no legacy schema mutation.
- If choosing reset/reinvite over password-hash migration, make lockout/remediation explicit so staff are not silently stranded.
</threat_model>

Remote rehearsal on `dgfy-temp` / `~/dgfy-rehearsal-template` proved product/inventory target data across 26 business DBs:

- schema migrate: success, 234 migrations executed
- data dry-run: success, 2144 planned inserts, 34 skips, 0 conflicts, 26 tenants
- data apply: success, 2084 writes, 2 skips, 0 conflicts
- retry apply: success, 0 writes, 2124 reconciled
- verify: all 26 `data_migration.targets` passed, but global `data_migration_ok=false` due open `missing_accepted_membership` findings

The issue is not product/inventory fidelity. It exposed that the verifier and architecture treat pending/accepted DGFY membership as mandatory staff access evidence, while the intended product model requires tenant-local staff credentials independent of DGFY account linking.
