## User Constraints (from CONTEXT.md)

### Locked Decisions

- **D-13.5-01:** DGFY global accounts are optional for staff, not mandatory.
- **D-13.5-02:** Tenant-local staff credentials must exist as first-class target data, either directly on `staff_accounts` or in a same-tenant `staff_credentials` table. The exact table shape is this phase's design decision; do not continue with the current no-credential staff schema unchanged.
- **D-13.5-03:** `account_staff_assignments` remains useful, but it represents optional DGFY-account linkage to a tenant-local staff profile. It is not the only staff access path.
- **D-13.5-04:** Legacy `tenant_db.users.password_hash` must be migrated or intentionally invalidated with an explicit reset/reinvite flow. No silent discard.
- **D-13.5-05:** Pending DGFY memberships/invites are not product/inventory blockers. Accepted DGFY memberships should link when valid, but missing/pending DGFY membership does not imply a staff account cannot exist or log in tenant-locally.

**Current Conflict (from CONTEXT.md):** ADR 0028 currently says: IMS user invitations are DGFY-account invitations; tenant-local password setup for invited business users is retired by default; new invited users must be selected registered DGFY accounts; POS DGFY unlock and IMS switcher require accepted DGFY membership. That conflicts with the intended product requirement. This phase must amend ADR 0028 rather than work around it in migration code.

### Claude's Discretion

- The exact credential table shape (columns on `staff_accounts` vs. a same-tenant `staff_credentials` table) is this phase's design decision (per D-13.5-02).

### Deferred Ideas (OUT OF SCOPE)

- None recorded in CONTEXT.md.

### Threat Notes (from CONTEXT.md — binding)

- Do not infer DGFY account access from matching email/phone. Optional DGFY linking must still require explicit link proof.
- Do not expose password hashes, POS PIN hashes, raw invite tokens, reset tokens, or temporary passwords in migration reports.
- Tenant-local staff credential migration must be additive and reversible enough for rehearsal reset; no legacy schema mutation.
- If choosing reset/reinvite over password-hash migration, make lockout/remediation explicit so staff are not silently stranded.

## Summary

Phase 13.5 is a codebase-internal cross-boundary correction, not a new-technology phase. Everything needed already exists in the repo: the amendment pattern (ADR 0029's `## Amendment` section, added by Phase 12), the additive-schema-migration pattern (`20260716100000-extend-schema-for-legacy-migration.cjs`, which also documents the contract-update-in-same-commit invariant), the pure-mapper + `related_targets` pattern (`mappings.js` entity 2 writes `tenant_ownership_metadata` as a related write), and the expected-non-blocking-findings pattern (`verifyData.js`'s `EXPECTED_LOSSY_REASON_CODES` set, which lets `lossy_category_collapse` findings stay auditable without failing `data_migration_ok`). The phase composes these four existing patterns.

Research confirmed three facts that materially shape planning. First, **hash compatibility is a non-issue**: legacy backend and `dgfy-api` both use `bcryptjs ^2.4.3` (`authService.js` hashes with `genSalt(10)`; `accountUseCases.js` compares with injected `bcrypt.compare`), and the landlord accounts migration (entity 1) already copies `password_hash` byte-for-byte as precedent. Second, **not every legacy `password_hash` is a credential**: legacy invited-pending users are created with the literal placeholder string `'PENDING_INVITATION'` (`userService.js:1688`), so the mapper must classify real bcrypt hashes (`/^\$2[abxy]\$/`) vs. placeholders — placeholder users get a documented reinvite path, never a copied "credential." Third, **two latent defects sit directly in this phase's blast radius**: (a) `mapLegacyUserToStaffAccount` emits `status: 'inactive'` but the `staff_accounts` ENUM is `('active','suspended','removed')` — an invalid enum value (the accounts mapper has the same defect against ENUM `('active','suspended','deleted')`); and (b) the dry-run JSON report writes raw mapper `target_payload` to disk (`data.js` `results: entries`, no redaction in `reportWriter.js`), which means landlord account password hashes already leak into dry-run report files today — adding staff credential hashes to payloads without fixing this would violate this phase's threat notes.

**Primary recommendation:** Plan four work surfaces in dependency order — (1) ADR 0028 amendment + governed-doc updates, (2) additive `staff_credentials` schema migration + `dgfyBusinessContract.js` update in the same commit, (3) mapper extension (credential classification, placeholder handling, enum fix, report redaction), (4) verify split (`staff_auth` section separate from product/inventory fidelity, membership findings non-blocking for `data_migration_ok`). No new packages. No legacy schema mutation.

### Pattern 1: ADR Amendment Section (in-repo precedent)

**What:** Append a dated `## Amendment` section to the existing ADR instead of rewriting decision history; state explicitly which original rules no longer hold and which survive.
**When to use:** Correcting an accepted ADR whose original decision text conflicts with product intent.
**Example:**

```markdown
<!-- Source: docs/architecture/adr/0029-...md lines 125-156 (Phase 12 precedent) -->
## Amendment (v2.1 Phase 13.5 Staff Authentication Model Correction, 2026-07)

[what changes, numbered]...

This amendment does not change [rules that survive: explicit-membership
non-inference, no company_token exposure, ownership transfer step-up, ...].

`status: accepted` is preserved; this is an amendment, not a revision of the
original decision history.
```

**Critical nuance:** unlike ADR 0029's amendment (which only widened scope), this amendment *replaces* decision rules. The amendment must name each superseded sentence-level rule (DGFY-only invitations; retired tenant-local password setup; grace-deadline blocking of unlinked users; "must not create new non-DGFY users") so `lint:docs` consumers and future readers can't cite the superseded text as authoritative.

### Pattern 2: Recommended `staff_credentials` table shape (Claude's discretion under D-13.5-02)

**Recommendation:** separate same-tenant `staff_credentials` table, NOT columns on `staff_accounts`.

**Why:** (a) `staffOnboardingRepository.toPlainStaffAccount()` and any staff list/profile endpoint serialize whole `staff_accounts` rows — a separate table makes hash exposure structurally impossible rather than filter-by-convention (the same argument `dgfy-data-migration-map.md` entity 7 makes for terminal secrets); (b) purely additive — zero ALTER on an already-populated rehearsal table; (c) credential absence is meaningful state (staff without tenant-local login = DGFY-linked-only staff), cleanly modeled as row-absence instead of NULL-tuple semantics.

```javascript
// Proposed DDL (follow 20260711143000-add-dgfy-business-staff-invitations.cjs shape)
staff_credentials: {
  id:                     INTEGER PK autoIncrement,
  staff_account_id:       INTEGER NOT NULL UNIQUE,        // FK -> staff_accounts.id, CASCADE
  password_hash:          STRING(255) NULL,               // bcrypt, copied byte-for-byte
  pos_approval_pin_hash:  STRING(255) NULL,               // bcrypt (legacy uses same hashPassword())
  credential_status:      ENUM('active','reset_required','disabled') NOT NULL DEFAULT 'active',
  password_updated_at:    DATE NULL,
  created_at / updated_at
}
// indexes: unique_staff_credentials_staff_account (staff_account_id), idx_staff_credentials_status
```

`credential_status='reset_required'` is the explicit representation of the D-13.5-04 "intentionally invalidated with reset/reinvite" branch (e.g., legacy placeholder-hash users) — staff are visibly flagged, never silently stranded (threat note 4).

### Pattern 3: Credential migration via `related_targets` (existing mapper mechanism)

**What:** `mapLegacyUserToStaffAccount()` returns a `related_targets` entry for the `staff_credentials` write, exactly as `mapLegacyTenantToBusiness()` does for `tenant_ownership_metadata` (migration map entity 8: "a direct 1:1 derived write from the mapper's own inputs, not an independently ID-mapped entity").
**Classification rule (from verified legacy behavior):**

```javascript
// Legacy invite creation (backend/src/services/userService.js:1688):
//   password_hash: 'PENDING_INVITATION'  ← literal placeholder, NOT a hash
const REAL_BCRYPT = /^\$2[abxy]\$\d{2}\$/;
if (REAL_BCRYPT.test(legacyUser.password_hash)) {
  // related_target: staff_credentials insert — hash copied unchanged,
  // never re-hashed, never logged (entity-1 precedent, migration map line 101)
} else {
  // No credential row OR credential_status='reset_required';
  // structured finding (new reason_code, e.g. 'staff_credential_reset_required')
  // — documented reinvite path, not silent discard (D-13.5-04)
}
```

**Idempotency:** `staff_credentials` inherits the staff account's `legacy_id_map` row (related write, entity-8 pattern) — apply retries must skip-if-exists on `staff_account_id` unique key.

### Pattern 4: Verify split via expected-reason-code set (existing mechanism)

**What:** `verifyData.js` already has `EXPECTED_LOSSY_REASON_CODES` — findings in the set stay visible (`expected_lossy_findings`) but don't block `data_migration_ok` (`checkOpenFindings()`, lines 139-172). Add a parallel `STAFF_LINKAGE_REASON_CODES` set (`missing_accepted_membership`, `orphan_tenant_user_link`, plus any new staff-credential codes) and a separate `staff_auth` report section with its own `staff_linkage_ok`/counters.
**When to use:** exactly criterion 5 — "Phase 13 data proof is not red because a pending DGFY invite exists" while accepted-staff credential migration remains auditable.
**Keep:** `checkRequiredRelationships()`'s rule that an *existing* `account_staff_assignments` row must be backed by an accepted membership — that is still a real integrity violation (a linkage row without link proof), distinct from a *pending* membership that merely produced a skip.

### Anti-Patterns to Avoid

- **Email/phone-inference linking:** never create assignments/memberships from contact-field matches — the amendment relaxes *mandatoriness* of DGFY linking, not the *evidence rule* for linking (CONTEXT threat note 1; ADR 0028 non-inference rule survives).
- **Working around ADR 0028 in migration code:** CONTEXT explicitly requires amending the ADR first; governance requires ADR resolution before cross-boundary implementation.
- **Mutating legacy schema or legacy `users` rows:** legacy is a read-only source (CMP-02, threat note 3).
- **Blanket-unblocking all findings:** only staff-linkage codes become non-blocking; `missing_required_field`, `duplicate_email`, `owner_mismatch` etc. must still block.
- **Putting hashes in `target_payload` without fixing report redaction first:** see Pitfall 2.

## Common Pitfalls

### Pitfall 1: Invalid ENUM value `'inactive'` in the staff (and accounts) mappers
**What goes wrong:** `mapLegacyUserToStaffAccount()` (mappings.js:574-576) emits `status: 'inactive'`, but `staff_accounts.status` ENUM is `('active','suspended','removed')` (migration `20260710021000`:97). `mapLegacyAccountToDgfyAccount()` (mappings.js:285) has the same defect against `accounts` ENUM `('active','suspended','deleted')`. `dgfy-data-migration-map.md` documents the invalid value as intended (entity 1 & 4). In MySQL strict mode the insert errors; in non-strict mode it silently coerces to `''`.
**Why it happens:** mapper written from doc prose, not the applied ENUM; legacy invited-pending users are exactly the `is_active=false` cohort, so this phase's changes will hit it.
**How to avoid:** fix in this phase (it's in the touched mapper): map `is_active=false` → `'suspended'` (no DDL) or additively extend the ENUM; correct the migration map doc either way; add a unit test asserting every emitted status is in the target ENUM.
**Warning signs:** apply errors on inactive users, or `status=''` rows in rehearsal targets.

### Pitfall 2: Dry-run reports write raw `target_payload` — hashes leak to disk
**What goes wrong:** `commands/data.js` puts `results: entries` (full mapper output incl. `target_payload`) into the dry-run JSON report; `reportWriter.js` does no redaction. The accounts mapper already puts `password_hash` in `target_payload` — so dry-run report files on the rehearsal host already contain landlord password hashes. Adding staff credential hashes to payloads would widen the leak and directly violate this phase's threat note 2. (The apply report is safe: `apply.js:438` deliberately omits payloads.)
**Why it happens:** dry-run was designed for evidence richness; entity 1 predates the staff threat notes.
**How to avoid:** redact/omit credential-bearing fields (`password_hash`, `pos_approval_pin_hash`) from dry-run report entries — either structurally (mapper emits `has_password_hash: true` evidence flags in payload and apply re-reads the source) or at report-assembly time. Add a verify check: report files contain no `$2a$/$2b$` substrings.
**Warning signs:** `grep -r '\$2[ab]\$' <reportDir>` returns hits.

### Pitfall 3: Treating `'PENDING_INVITATION'` placeholder as a migratable credential
**What goes wrong:** legacy invite creation sets `password_hash: 'PENDING_INVITATION'` and `is_active:false` (`userService.js:1685-1695`); acceptance later sets the real hash. Blind hash-copy stores a non-hash string as a "credential," misrepresenting credential coverage (it can't verify, so not exploitable, but it corrupts the STAFF-03 audit trail).
**How to avoid:** classify with `/^\$2[abxy]\$\d{2}\$/`; placeholder/pending users get no credential row (or `reset_required`) plus a structured finding; migrate legacy invitation state intentionally (pending legacy invites → documented reinvite flow via `staff_invitations`, or explicit finding).
**Warning signs:** `staff_credentials.password_hash` rows failing the bcrypt-format check.

### Pitfall 4: Schema migration and `dgfyBusinessContract.js` drifting apart
**What goes wrong:** a table/column/index absent from the contract is never checked by `verify` — schema verification silently passes while the target is wrong. Phase 12 flagged this as "the single most important cross-file relationship" (T-12-04).
**How to avoid:** update `dgfyBusinessContract.js` in the SAME commit as the new migration; also update the dgfy-api `StaffCredential.js` model to match the applied migration exactly (repo convention: model mirrors real migration over plan prose — `AccountStaffAssignment.js` header documents a past instance of this divergence).

### Pitfall 5: Over-unblocking verification
**What goes wrong:** dropping `missing_accepted_membership` findings entirely (or making all skips non-blocking) destroys the auditability that criterion 5 explicitly requires ("accepted staff credential migration remains auditable") and weakens unrelated gates.
**How to avoid:** scope the non-blocking set to staff-linkage codes only; keep a dedicated `staff_auth` section with per-tenant linkage/credential counters; keep `checkRequiredRelationships()`'s existing-assignment-without-membership violation as blocking (that's corrupt linkage, not pending linkage).

### Pitfall 6: `account_staff_assignments` unique constraint surprise
**What goes wrong:** the real applied constraint is UNIQUE on `dgfy_account_id` ALONE (one DGFY account → at most one staff assignment per tenant DB), not the composite `(dgfy_account_id, staff_account_id)` that early plan prose described (`AccountStaffAssignment.js` header). Linkage-repair logic that assumes multiple assignments per account per tenant will conflict.
**How to avoid:** design linkage semantics around the single-assignment-per-account-per-tenant invariant; don't "fix" the constraint in this phase (out of scope, already-populated tables).

### Pitfall 7: Amending ADR 0028 without disposing of dependent rules
**What goes wrong:** ADR 0028 weaves the DGFY-only rule through many consequences: grace-cohort deadline (2027-06-17), POS unlock requiring accepted membership, "must not create new non-DGFY users", invite-link retirement, registration-disabled flags. Amending only the invitation sentence leaves contradictory authoritative text.
**How to avoid:** amendment enumerates each affected rule with explicit disposition (superseded / survives / reframed). Rules that must SURVIVE: explicit-membership non-inference for DGFY linking, no `company_token` exposure, ownership-transfer step-up, tenant-session bridge via accepted membership. Run `npm run lint:docs` (governed-docs gate).

## Open Questions

1. **How far into `apps/dgfy-api` does "assumptions must converge" reach?**
   - What we know: success criteria require schema + docs + migration + verify; `staffOnboardingRepository.js` encodes the wrong assumption in `createStaffAccount()` (no `initialPassword` by design) and `StaffAccount.js`/contract doc comments repeat it; no staff login route exists in `dgfy-api` today.
   - What's unclear: whether this phase must add credential *write paths* in the API (invitation-accept-with-password-setup) or only correct models/comments/contracts so nothing contradicts the amended ADR.
   - Recommendation: minimal API convergence in this phase (new `StaffCredential.js` model, corrected doc comments/contracts, `staffOnboardingRepository` comment fix); defer the login/invitation-password-setup endpoint to a dedicated phase — it triggers the full ARCHITECTURE_GOVERNANCE hardening contract (replay, lifecycle, rendered-UI proof) that would balloon this blocker phase. Surface at plan time for user confirmation (relates to A3).
2. **Disposition of already-persisted `missing_accepted_membership` findings from the Phase 13 run.**
   - What we know: findings are durable rows in `dgfy_migration_meta.data_quality_findings`; verify reads open findings per `run_scope`.
   - What's unclear: whether Phase 13's proof is re-established by re-running `verify` alone (new semantics re-classify the same open findings as non-blocking) or requires a fresh dry-run/apply/verify cycle in a new run scope.
   - Recommendation: design verify so re-running `verify` on the existing run scope yields `data_migration_ok=true` with the same findings visible under `staff_auth` — cheapest re-proof; confirm against rehearsal host.
3. **Legacy pending-invitation users: migrate as `staff_invitations` rows or findings only?**
   - What we know: legacy pending invites are `users` rows with placeholder hash + `invitation_status='pending'` + hashed `invitation_token`; new `staff_invitations` exists with SHA-256 token_hash (different token, can't be carried over — legacy tokens are legacy-URL-bound).
   - Recommendation: do NOT carry legacy invite tokens; migrate pending-invite users as staff profile + `reset_required`/no-credential + structured finding naming the reinvite path. Tokens are secrets and legacy-flow-bound (threat note 2).
4. **`staff_accounts` inactive-status representation** — map `is_active=false` → `'suspended'` (no DDL) vs. additive ENUM extension `'inactive'`. Recommendation: `'suspended'` (zero DDL on populated tables, semantically equivalent); update the migration map text accordingly.
