<objective>
Close the folded pending todo (explicitly pulled into Phase 12 scope by the user): `buildReviewComplianceStateUseCase` currently calls `recordVerification()` then `upsertState()` as two independent, non-transactional writes (`complianceUseCases.js:308-320`). A crash or race between them can record a compliance review while leaving `compliance_mode_state.state` un-demoted — so a `compliant_active` business whose fiscal paperwork is revoked keeps `ALLOW` for Fiscal POS_CHECKOUT (a fail-open / TOCTOU window, HTTP-reachable via `POST /compliance/review`). This protects the integrity guarantee behind FSC-01 (the compliance-mode state must actually reflect verification).

Purpose: Make the verification write and the state demotion a single atomic, row-locked unit — the primary security-relevant change of this phase.

Output: New `recordVerificationAndState()` repository method (transaction + `lock: t.LOCK.UPDATE`), the usecase switched to it, and an atomicity regression test. This is separate from the schema work (touches `dgfy-api`, not the migration-runner) and runs in parallel with Plans 01/02.
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| client → POST /compliance/review | An authorized reviewer submits a review outcome; the state demotion must be atomic with the verification record or a partial write leaves a stale ALLOW |
| concurrent review requests → compliance_mode_state row | Two reviews (or a crash mid-write) racing on the same row |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-12-07 | Elevation of Privilege / Tampering | non-atomic verify+state leaves stale compliant_active (Fiscal POS_CHECKOUT fail-open) | high | mitigate | Single `sequelize.transaction()` + `lock: transaction.LOCK.UPDATE` writing verification triplet + state in one `record.update()` (recordVerificationAndState) |
| T-12-08 | Tampering | concurrent reviews double-write / lost update on the state row | high | mitigate | `lock: transaction.LOCK.UPDATE` serializes concurrent reviews on the row (same proven Phase 8 CR-02/CR-03 pattern) |
| T-12-09 | Tampering | review recorded without an evidence row (contract bypass) | medium | mitigate | `findOne` + `ComplianceStateNotFoundError` (no `findOrCreate`) preserves "submit evidence before review" → 404 |
| T-12-SC | Tampering | npm/pip/cargo installs | low | accept | Zero packages installed; edits existing repository/usecase/test files only |
</threat_model>
