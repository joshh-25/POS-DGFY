<threat_model>
OWASP ASVS Level 1 framing: verification is a release evidence boundary. False-positive verification is high risk because later phases build APIs and migrations on this schema.

## Trust Boundaries
| Boundary | Description |
|---|---|
| Database metadata -> verification report | `information_schema` and metadata rows become operator evidence. |
| `dgfy_core` registry -> business DB coverage | Registry rows determine which tenant schemas are expected. |
| Legacy schema fingerprints -> non-mutation proof | Legacy compatibility safety depends on trustworthy before/after comparison. |

## STRIDE Threat Register
| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|---|---|---|---|---|---|
| T-02-04-01 | Repudiation | migration metadata verification | high | mitigate/block | Verify target-scoped `schema_migrations` records for Phase 02 migrations and command execution status/report paths. |
| T-02-04-02 | Tampering | legacy non-mutation fingerprints | high | mitigate/block | Capture a durable pre-migration baseline, then compare post-migration `information_schema` fingerprints across tables, columns, indexes, and constraints for `sku_*`. |
| T-02-04-03 | Spoofing | tenant coverage | high | mitigate/block | Cross-check explicit `dgfy_business_*` targets against `business_database_registry` when available and flag gaps. |
| T-02-04-04 | Denial of Service | verification command | medium | mitigate | Verification should report failed checks without crashing on expected missing-schema states; unexpected command failures still mark metadata failed. |
| T-02-04-05 | Information Disclosure | verification reports | medium | mitigate | Reports include schema names/findings only; do not include DB passwords, tokens, or connection strings. |
</threat_model>
