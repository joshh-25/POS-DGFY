<objective>
Close FSC-01, the single BLOCKING gap in 08-VERIFICATION.md (status: gaps_found). The compliance-review use case buildReviewComplianceStateUseCase (complianceUseCases.js:274-329) only writes compliance_mode_state.state when verificationStatus === 'verified'. For 'rejected'/'revoked' outcomes it patches only the verification metadata (via recordVerification) and leaves state untouched — so a business that reached compliant_active and is later reviewed 'revoked' (e.g. a forged BIR accreditation is discovered) keeps state: compliant_active forever, and evaluateComplianceDecision() — which branches exclusively on the state column — keeps returning ALLOW for a Fiscal POS_CHECKOUT. This is a fail-open authorization bypass (the same class the FSC-02 closure just fixed one layer up, in the evidence checklist).

DECISION (locked by user this session, authoritative, not in any file):
- On a 'rejected' OR 'revoked' review outcome, buildReviewComplianceStateUseCase MUST transition compliance_mode_state.state to COMPLIANCE_MODE_STATE.NON_COMPLIANT_ACTIVE (the fully fail-closed default). This makes evaluateComplianceDecision() return NON_COMPLIANT_FISCAL_DOCUMENT_BLOCKED for a Fiscal POS_CHECKOUT (fiscal denied) while keeping non-fiscal allowed, consistent with D-02/D-05.
- Do NOT extend the API to require an explicit newState on reject/revoke (option rejected by user). The demotion is unconditional to non_compliant_active.
- State-demotion is the chosen single source of truth: the executor demotes state rather than adding a parallel verification_status branch into complianceGate.js/evaluateComplianceDecision(). With the state correctly demoted, the gate's existing state-based branch is sufficient; no plumbing change to the gate/policy engine is required for correctness.

This is a security fix (fail-open authorization bypass), not a design change — Option A shape mirrors the 08-09/08-10 gap-closure precedent exactly.

Purpose: Make compliance_mode_state.state truthfully reflect whether required fiscal paperwork is currently present AND verified across the full revoke/reject lifecycle, so Phase 9 inherits a gate that cannot be silently bypassed after a revocation.
Output: reject/revoke demotion in buildReviewComplianceStateUseCase + a corrected JSDoc + one new regression test file proving a revoked/rejected compliant_active business no longer reaches ALLOW for Fiscal POS_CHECKOUT.
</objective>
