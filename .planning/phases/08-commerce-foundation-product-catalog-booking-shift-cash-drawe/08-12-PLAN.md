<objective>
Close the two Critical missing-row-lock races surfaced by the fresh 08-REVIEW.md (CR-02, CR-03) and re-confirmed by direct code read in 08-VERIFICATION.md's Anti-Patterns section. Both are the same defect shape as the FSC-01 gap: a read-then-act guard that is not serialized under concurrent double-submit, in two independent modules.

- CR-02 (Critical) — bookingRepository.cancelBooking (~266-295): the guard read Booking.findByPk(Number(id), { transaction }) has no row lock, so two concurrent cancels of the same booking can both pass the `status === 'cancelled'` guard before either commits and both run the mirror `slots_remaining + 1`, double-releasing branch capacity. The create path already uses an atomic guarded UPDATE (D-08 / Pitfall 3); the cancel path must serialize its guard the same way.
- CR-03 (Critical) — shiftRepository.closeShift (~251-293): the guard read Shift.findOne({ where, transaction }) has no row lock, so two concurrent closes can both pass the `status !== 'open'` guard, write two 'close' cash_drawer_events, and lose-update the reconciliation figures.

DECISION (locked by user this session): close BOTH lock-races in this round. Fix = add a `FOR UPDATE` row lock (`lock: transaction.LOCK.UPDATE`) to each guard read so concurrent operations serialize; the second operation sees the terminal status and is rejected with the existing named error, without a second capacity release / duplicate close event. This is a surgical, minimal-scope hardening — no schema change, no behavior change on the happy path.

Purpose: Harden the booking and shift modules against concurrent double-submit before Phase 9 (Checkout) builds directly on them under real concurrent load, so capacity accounting and shift reconciliation cannot silently corrupt.
Output: A `lock: transaction.LOCK.UPDATE` on each of the two guard reads + two new mocked unit test files pinning the source lock and the reject-second-operation behavior.
</objective>
