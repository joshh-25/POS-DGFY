<objective>
Fix the confirmed MySQL error 1215 blocker (08-UAT.md Test 1, severity: blocker) that prevents `20260712100000-create-commerce-foundation.cjs` from applying to any real `dgfy_business_*` tenant database, and close a second, previously-unexercised instance of the exact same defect discovered while investigating: `compliance_mode_state.branch_id` (also fixed by this migration) feeds `branch_scope_key`, a STORED generated column added later by `20260712140000-harden-compliance-mode-state-uniqueness.cjs` — and it carries the identical CASCADE-on-a-generated-column-base-column defect. Fixing only `shifts` would leave the migration chain failing one file later, on the exact same error, so both must be fixed together for the diagnosed gap's truth ("Running the 08-01/08-09 migrations against a real dgfy_business_* tenant results in ok:true") to actually become reachable.

Root cause (confirmed via official MySQL 8.0 docs): a foreign key constraint on the BASE column of a STORED generated column cannot use CASCADE, SET NULL, or SET DEFAULT for either ON UPDATE or ON DELETE — only RESTRICT/NO ACTION are permitted in either direction. `shifts.terminal_id`/`shifts.cashier_account_id` (base columns of `active_terminal_cashier_key`) and `compliance_mode_state.branch_id` (base column of `branch_scope_key`) all currently declare `onDelete: 'CASCADE', onUpdate: 'CASCADE'`, which MySQL/InnoDB rejects with error 1215 the moment the dependent generated column's `ALTER TABLE ... ADD COLUMN ... STORED` runs.

Fix: switch all three FKs' `onDelete`/`onUpdate` from `'CASCADE'` to `'RESTRICT'` in the migration (and the two Tenant Sequelize models ported from it, to prevent drift). This is a zero-behavior-change fix in practice — grep-confirmed: no code in this repo ever hard-deletes a `terminal_identities`, `staff_accounts`, or `locations` row; `locationRepository.delete()` is a soft delete (`is_active = false`), and no equivalent hard-delete path exists for terminals or staff accounts.

Since `20260712100000` has never been successfully applied to any real business database (08-01/08-09's own SUMMARYs record only mocked-queryInterface/grep verification; 08-UAT.md's real-MySQL run is the first live attempt, and it failed), this plan edits the migration file directly rather than writing a corrective forward-dated migration.

Purpose: Unblock 08-UAT.md's Test 1 (and by extension the two migration-dependent UAT items blocked on it — append-only trigger firing and real-concurrency lock reproduction — though re-running those against live MySQL remains a human/operator step, same as the original UAT). Without this fix, no downstream Phase 9/10/11 work can run its own migrations against a real business tenant either, since the chain never gets past this point.

Output: Corrected referential actions in the migration and its two ported Tenant models, plus a new real-MySQL-gated Jest integration test (`phase08CommerceFoundationSchema.test.js`, mirroring the existing Wave-7 `phase04StaffInvitationsSchema.test.js` pattern) that proves the full chain applies cleanly and that both DB-level uniqueness invariants (one-open-shift, one-row-per-branch) actually materialize on real MySQL — the automated regression evidence that a bug of this shape was missing until now.
</objective>
