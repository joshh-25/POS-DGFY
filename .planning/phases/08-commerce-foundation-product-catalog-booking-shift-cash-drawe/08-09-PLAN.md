<objective>
Close the two BLOCKER gaps that verification (08-VERIFICATION.md) confirmed in the `modules/compliance` module — both originally built by 08-06-PLAN.md. Everything else in Phase 08 passed and is out of scope.

- CR-01 (FSC-01): the compliance-mode-state write path has a TOCTOU race, and its DB unique index cannot enforce one-row-per-business when `branch_id IS NULL` (MySQL treats every NULL as distinct). Fix = make the invariant DB-enforceable for the no-branch case + make the write atomic + map the conflict to a clean 409.
- CR-02 (FSC-02): the `compliant_active` POS-operation gate branch returns ALLOW after checking only profile/settings/artifacts/peripherals, ignoring the other evidence-derived readiness signals (RMO filing, fiscal-terminal registration, audit-append-only, payment-handoff, encryption prerequisites, documentary readiness, fiscal-accumulator) that the same function already computes — contradicting complianceGate.js's own header comment.

DESIGN DECISION (CR-02) — both options from 08-REVIEW.md surfaced:
- Option A (RECOMMENDED, implemented here): enforce the full evidence-derived checklist in the compliant_active POS branch, mapping each unmet signal to its own REQUIRES_SETUP reason code.
- Option B (rejected): leave the narrower behavior and merely correct the header comment + add a TODO + pin the gap with a regression test.
Rationale for A: CR-02 is a real authorization / business-logic bypass (a compliant_active business with an unregistered fiscal terminal or incomplete RMO filing gets ALLOW for POS_CHECKOUT). Security enforcement is active at ASVS L1, block-on-high, and this is a high-severity bypass — Option B would only document the hole, not mitigate it, so it cannot satisfy the block-on-high gate. All the per-signal reason codes and the `ready_for_compliant_activation` roll-up are already computed by evaluateComplianceChecklist(), so wiring them into the decision is surgical and low-risk. With Option A in place, complianceGate.js's header comment becomes accurate (empty evidence now correctly yields REQUIRES_SETUP), so we tighten the comment rather than weaken it.

Purpose: Restore FSC-01 (exactly one compliance_mode_state row per business/branch, atomically) and FSC-02 (one shared gate that actually enforces the full checklist it documents), without regressing the D-05 deviation.
Output: A new forward migration + contract/model sync, an atomic repository write path with a 409 mapping, a full-checklist compliant_active gate, and two mocked (no-live-MySQL) unit test files pinning both fixes.
</objective>
